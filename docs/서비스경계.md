| Payment (공용 Gradle 모듈) | PG(포트원) 실제 호출(운영 `portone-live` 프로필, 로컬은 Mock), 결제 생성·단건조회 검증·취소·환불, 환불 실패 재시도 배치, PaymentTransaction 엔티티 정의와 결제 상태 전이, 웹훅 서명검증(Raw Body 기준)과 동기화 함수(결과를 모르면 처리 완료로 적지 않아 재전송을 받는다), webhook_events 템플릿 제공 | 없음(코드만 소유). 테이블은 모듈을 참조하는 각 Service가 자기 Schema에 직접 Migration | #5, #6, #10 | 예약 결제와 VIP 배너 결제가 같은 PG 연동 코드를 쓰지만 결제 레코드는 각 도메인이 소유해야 한다. 코드만 공유하고 데이터는 분리하는 방식으로 중복 구현과 소유권 침범을 동시에 피한다 | 별도 Payment-Service로 분리 — 결제 레코드를 한 서비스가 독점하게 되어 “FK는 같은 Service DB 안에서만” 원칙과 정산 조회 구조가 무너져 기각 | 확정 |
| Settlement-Service | 당일·주간·월간·연간 매출·환불·수수료 집계, 박람회 예약과 VIP 배너 매출 분리, 날짜별 달력·박람회/분야 랭킹, 정산 AI 요약, 전체관리자 정산 대시보드 | 없음 — 결제 레코드를 조회 시점에 집계하며 자기 Table을 갖지 않는다 | #11, AI-6 | 정산은 조회 시점에 계산하는 파생 지표라 실시간 트랜잭션(Reservation)과 변경 주기·부하 특성이 다르다. 결제 테이블을 직접 갖지 않는 이유는 “FK는 같은 Service DB 안에서만” 원칙과 같다 | Reservation-Service에 흡수 — 이번 프로젝트 규모라 부하 특성 차이가 크지 않지만, 팀에서 별도 유지로 결정 | 확정 (Sprint 3 생성, Sprint 4 개편) |
| Ticket-Service | QR 발급·무효화, 현장 체크인(QR/예약번호) 검증과 되돌리기(티켓 단위 직렬화), 체크인 처리 이력 기록(커밋 후), 체크인 집계 제공, 체크인 결과 AI 요약 | Ticket(QR payload), CheckinLog(체크인 처리 이력) | #5, #7, #8(집계 제공), AI-3 | 다른 도메인과 결합도가 가장 낮고, 현장 체크인은 오프라인·저지연 요구가 있어 독립 배포 가치가 있음. 다른 서비스와 원자적 트랜잭션으로 묶여야 할 이유가 없어 Round와 달리 독립에 따른 리스크가 없음 | expo-service·Reservation-Service에 흡수 — 어느 쪽에 합쳐도 통신이 1~2개만 줄고 나머지는 남아 실익이 작아 기각 | 확정 |
| recommendation-service | 관심사 등록, 행동 이벤트 수집, 태그별 취향 점수 집계, 박람회 AI 자동 태깅·재태깅, 맞춤 추천 목록·유사 박람회·태그 조회 제공, 개인화 알림과 예약 확정 알림 생성·읽음 처리 | user_interests, user_activities, user_preference_scores, expo_tags, notifications | AI-1, #5(예약 확정 알림) | 추천·알림은 예약·결제와 변경 주기가 다르고, 추천 서비스 장애가 예약·체크인에 영향을 주어서는 안 됨. 모든 연동을 fail-open으로 두어 recommendation-service가 죽어도 핵심 기능 무영향 보장 | expo-service 내 모듈로 흡수 — 추천 기능이 확장될수록 expo 도메인과 결합도가 커져 기각 | 확정 |

> **Gradle 모듈 현황.** `settings.gradle` 에 등록된 모듈은 identity-service · expo-service · reservation-service · ticket-service · settlement-service · recommendation-service · common-security · common-payment · common-ai 9개다. common-security 는 JWT 검증 필터, common-payment 는 PG 연동, common-ai 는 Gemini 호출을 공용으로 제공하며 셋 다 자기 Table 을 갖지 않는다. Sprint 4 에 common-ai 가 추가됐다.

## 외부 의존

| 대상 | 쓰는 곳 | 무엇을 맡기나 | 실패 시 결과 | 비고 |
| --- | --- | --- | --- | --- |
| PortOne(PG) | common-payment 모듈 (Reservation-Service·expo-service가 사용) | 결제 생성·검증·취소·환불, 결제 웹훅 발신 | fail-closed. 검증 결과가 “모름”이면 예약을 확정도 취소도 하지 않는다 | 운영도 PortOne 테스트 채널 키로 실제 API 를 호출한다. 연동키(Secret)는 어떤 문서·저장소에도 평문으로 남기지 않는다. 환경변수와 gitignore 된 파일에만 둔다 |
| 구글·네이버·카카오(OAuth) | Identity-Service (구글은 브라우저가 받은 액세스 토큰을 tokeninfo 로 발급처(`aud`)·이메일 검증 여부까지 확인, 네이버·카카오는 인가 코드를 서버가 토큰으로 교환) | 소셜 로그인 사용자 확인(식별자·이메일·이름 조회) | 해당 제공자 로그인만 실패. 토큰·코드가 틀리거나 우리 앱에 발급된 토큰이 아니면 401 `SOCIAL_LOGIN_FAILED`, 제공자 장애·응답 지연(연결 2s·응답 3s)이면 503. 이메일 로그인은 영향 없음. 제공자 호출은 DB 트랜잭션 밖에서 해 지연이 커넥션 풀을 잡지 않는다 | Client Secret·REST 키는 환경변수(`GOOGLE_CLIENT_ID`, `NAVER_CLIENT_SECRET`, `KAKAO_CLIENT_SECRET` 등)에만 둔다. `GOOGLE_CLIENT_ID` 가 비면 구글 로그인은 전부 거절(fail-closed) |
| Cloudinary | 프론트엔드만 | 박람회 대표 이미지·행사 소개 이미지·프로필 사진 업로드와 CDN 변환 전송 | fail-open. 업로드가 실패하면 이미지 주소를 직접 입력하거나 이미지 없이 등록·수정을 계속할 수 있다 | 백엔드는 Cloudinary를 호출하지 않는다. 브라우저가 unsigned preset 으로 직접 올리고, 서버에는 결과 URL 문자열만 저장한다 |
| Gemini API(LLM) | common-ai 모듈 경유 — expo-service(자연어 검색·소개글 초안), Reservation(캘린더 제약 해석), Ticket(체크인 결과 요약), recommendation(자동 태깅·알림 문구), Settlement(정산 요약) | 문장 → 구조화 데이터 변환, 수치 → 요약 문장 | fail-open. 각 기능이 규칙 기반 폴백으로 대체하거나 AI 부분만 비운다 | 키는 각 Service 의 GEMINI_API_KEY 환경변수. 서비스별 일일 호출 한도·캐시·재시도는 common-ai 가 담당 |

> **Cloudinary API Secret 은 프론트 `.env` 에 넣지 않는다.** `VITE_` 로 시작하는 값은 빌드 시점에 브라우저 번들에 평문으로 박히므로, 넣는 순간 공개된다. 프론트가 갖는 값은 `cloud_name` 과 unsigned preset 이름뿐이다.

## 데이터 소유권

| 데이터 | 소유 Service | 생성·변경 책임 | 다른 Service 참조 방법 | 직접 DB 접근 |
| --- | --- | --- | --- | --- |
| User / Role | Identity-Service | 회원가입·로그인·계정 발급 시 생성·변경. 실명(`name`)은 가입 때 정해지고 바꾸지 않으며 겹쳐도 된다. 닉네임(`nickname`)은 UNIQUE 이고 가입 때 실명으로 시작하되 이미 쓰이면 “#숫자”를 붙인다(기존 회원은 V8 에서 실명을 닉네임으로 옮기고 중복이면 “#id”). 닉네임·비밀번호·프로필 사진 주소는 본인만 변경한다. 전체관리자 계정 1건은 identity-service의 V2 Migration(seed)이 최초 기동 시 생성하며, 비밀번호 Hash는 Migration 파일에 두지 않고 Flyway placeholder로 주입한다(application-local.yml 또는 배포 환경 변수, Git 제외) | JWT(sub에 userId 문자열, role에 Role 문자열)로 참조 — 별도 조회 호출 불필요 | 금지 |
| OauthAccount(소셜 계정 연결) | Identity-Service | 소셜 계정으로 처음 로그인할 때 생성. 제공자가 검증한 이메일과 같은 회원이 있으면 그 회원에, 없으면 비밀번호 없는 새 회원(USER)에 연결한다. 카카오가 검증되지 않은 이메일을 주면 `kakao_{id}@social.expohub.local` 대체 이메일을 써 기존 회원에 붙지 않게 하고, 이 도메인으로는 직접 가입할 수 없다. `(provider, provider_id)` UNIQUE 로 한 소셜 계정이 두 회원에 붙지 않는다. 소셜로 가입한 회원은 `users.password_hash` 가 비어 있다 | 참조하지 않음(Identity-Service 내부 처리) | 금지 |
| OrganizerApplication(주최자 신청) | Identity-Service | 회원이 신청하면 대기(PENDING)로 생성하고, 전체관리자가 승인(APPROVED, 주최자 역할 부여)·거절(REJECTED, 사유 기록)한다. 대기 중 신청이 있거나 이미 주최자인 회원은 새로 신청할 수 없다 | 참조하지 않음(Identity-Service 내부 처리) | 금지 |
| Channel | expo-service | 주최자의 채널 생성 요청 시 생성, 소유자만 수정. 한 주최자는 채널을 하나만 소유하며 `owner_id` UNIQUE 제약과 서비스 계층 검사로 이중 보장 | `GET /internal/v1/expos/{expoId}` 응답의 `channelOwnerId`로 소유권 확인 | 금지 |
| Expo | expo-service | 박람회 등록 시 생성, 소유자가 소개문·대표 이미지·장소·지역·분야 등을 수정(마감된 박람회는 수정 불가). 공개(HIDDEN→PUBLISHED)는 주최자가, 마감(→CLOSED)은 expo-service의 자동 마감 스케줄러가 10분 주기로 전이. 공개 상태에서 마지막 회차가 삭제되면 Reservation-Service의 요청으로 숨김(→HIDDEN)으로 되돌린다 | `GET /internal/v1/expos/{expoId}`, `GET /internal/v1/expos`(공개 박람회 목록), `GET /internal/v1/expos/titles?expoIds=`, `GET /internal/v1/expos/categories?expoIds=`, `PATCH /internal/v1/expos/{expoId}/unpublish` | 금지 |

### 통신 원칙

- 모든 Service 간 호출은 동기 HTTP 이며 `/internal/**` 경로에 환경 변수로 주입한 공유 Bearer Token 을 부착한다. 이벤트 브로커를 도입하지 않는다
- `/internal/**` 은 Gateway(Nginx) 에서 404 로 차단해 외부에 노출하지 않으며, 외부 OpenAPI 문서에도 포함하지 않는다
- 외부 경로의 라우팅은 로컬(`nginx.conf`)과 운영(`nginx.prod.conf`) 두 파일에 같은 규칙을 둔다. 한쪽에만 규칙이 있으면 운영에서만 404 가 나는데, 화면이 조용히 무시하는 호출(조회 이벤트 등)은 그 증상이 드러나지 않는다
- 내부 API 의 성공 응답에는 공통 봉투를 씌우지 않고 raw 로 내보내며, 오류만 봉투로 감싼다. 한쪽이 봉투를 씌우고 다른 쪽이 raw 로 읽으면 전 필드가 null 인 객체가 만들어지는데 Jackson 이 예외를 던지지 않아 무증상으로 넘어간다. recommendation-service 의 내부 API 는 봉투를 씌우지만, 호출자가 응답 본문을 읽지 않는 알림성 호출이라 예외로 둔다
- 호출자는 `X-Trace-Id` 를 그대로 전파해 서비스 간 요청을 한 흐름으로 추적할 수 있게 한다. expo·reservation·ticket 사이의 핵심 호출은 전파하고, Settlement·recommendation 연동은 아직 전파하지 않는다
- 실패 정책은 세 가지로 구분한다. fail-closed(쓰기·정산·입장 여부 확인·정렬과 기간 조건 — 거절하고 상태를 바꾸지 않는다), fail-open(티켓 통지·추천 연동·부가 검증·표시용 조회 — 주 작업은 성립시키고 재시도하거나 건너뛴다), 부분 실패 허용(조회 — 가져온 것만 보여주고 실패한 부분을 구분해 표시한다)
- 표시용 데이터는 언제나 fail-open 이다. 박람회 제목·회차 번호·유료 무료 배지는 못 받아오면 화면이 id 로 물러날 뿐, 예약·체크인 같은 핵심 동작을 막지 않는다
- 조회 결과의 정확성이 곧 기능인 경우는 fail-closed 다. 모집마감일순 정렬과 자연어 검색의 기간 조건은 틀린 순서·틀린 목록을 보여주느니 503 으로 알린다
- 같은 결과를 만드는 전이는 경로가 갈라지지 않게 한 함수로 모은다. 예약 결제 확정은 사용자 호출·PG 웹훅·만료 배치 세 경로가, 배너 결제 확정은 화면의 결제 확인·PG 웹훅 두 경로가 각각 같은 멱등 함수를 탄다. 어느 경로든 PG 에 결제·금액을 직접 확인하고, 화면이 “결제됐다”고 알려온 것만으로는 상태를 바꾸지 않는다
- PortOne 웹훅은 예약·배너 모두 common-payment 의 서명 검증을 거친다. 같은 webhook-id 는 한 번만 처리하되, 결제 결과를 알 수 없어 503 을 준 웹훅은 처리 완료로 적지 않아 PortOne 의 재전송이 실제로 다시 처리된다
- 동시 요청으로 깨질 수 있는 불변식은 서비스 검사에 더해 DB 제약으로 막는다. 정원 초과는 조건부 UPDATE, 회원당 중복 예약은 생성 컬럼 UNIQUE 가 최종 방어선이다
- 두 Service 의 상태를 함께 바꿔야 할 때는 되돌릴 수 있는 로컬 변경을 먼저 하고, 되돌릴 수 없는 원격 호출을 트랜잭션 마지막에 둔다. 원격 호출이 실패하면 로컬 트랜잭션 롤백으로 함께 되돌린다. 실패할 수 있는 검증을 원격 호출 뒤에 두면, 검증이 실패할 때마다 원격 변경만 남는다. 마지막 회차 삭제가 이 순서를 따른다
- 부수 효과(티켓 통지·추천 이벤트·체크인 이력)는 주 트랜잭션이 커밋된 뒤에 보낸다. 커밋 전에 보내면 롤백돼도 상대 Service 에는 흔적이 남는다
- 행 잠금을 잡은 채 원격 호출을 하는 곳은 티켓 발급 통지와 체크인 확정 둘뿐이며, 둘 다 호출 상대가 우리 행을 다시 잠그지 않아 교착이 없고 타임아웃(2s+3s)으로 잠금 시간이 유한하다. 새로 추가할 때는 이 두 조건을 확인한다
- 여러 id 를 넘기는 조회는 한 번에 최대 200개로 나눠 호출한다. 받는 쪽 상한과 보내는 쪽 분할 크기를 같게 맞춰, 목록이 커져도 상한 초과로 실패하지 않게 한다
- LLM 호출은 Service 간 통신이 아니라 외부 의존이며, 모두 common-ai 를 거쳐 fail-open 으로 처리한다

### 소프트 삭제가 읽는 지점

삭제된 회차가 미래의 행동을 받는 경로는 필터하고, 과거의 이력을 보여주는 경로는 필터하지 않는다.

| 필터한다 (미래의 행동) | 필터하지 않는다 (과거의 이력) |
| --- | --- |
| 회차 목록(주최자·박람회 상세)·회차 수정 | 내 예약 목록·상세 |
| 새 예약 생성 | 정원 반환(release) |
| 박람회 공개 조건 | 발급된 티켓의 회차 시각 확인 |
| 자동 마감 판정 | 예약 취소 경로 |
| 유료·무료 배지 판정 | 정산용 결제 레코드 |
| 회차 번호 매김 | — |
| 모집마감일순 정렬·기간 조건 검색 | — |
| 캘린더 조회·AI 일정 추천 후보 | — |

다른 Service DB 조회·JOIN·갱신은 허용하지 않습니다. 이후 Sprint 계약은 위험을 확인하기 전까지 `PLANNED`로 둡니다.
