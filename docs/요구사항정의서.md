# 요구사항정의서 — 박람회 예약 관리 플랫폼

## 1. 사용자 문제·Product Goal·성공 기준

| 항목 | 정의 |
| --- | --- |
| 사용자 문제 | 박람회 주최사는 행사마다 예약·결제·입장 시스템을 별도로 구축해야 해 비용·시간 부담이 크고, 소규모 주최사는 수기 접수에 의존해 예약 데이터가 분산·중복·누락된다. 참가자는 현장 입장 시 명단 대조로 대기시간이 길다. |
| Product Goal | 여러 박람회를 하나의 플랫폼에서 채널 단위로 통합 관리·예약·결제·입장검수까지 처리하고, 주최자의 운영 효율과 참가자 예약 경험을 동시에 개선한다. |

### Release 성공 기준

- 주최자는 자신의 채널에 속한 박람회 데이터에만 접근할 수 있다 (채널 격리)
- 정원을 초과하는 예약과 같은 회원의 중복 예약은 동시 요청 상황에서도 성공할 수 없다
- 회원은 결제 완료 즉시 모바일 티켓을 발급받고, 현장에서 QR 또는 예약번호로 입장할 수 있다
- 예약 취소·환불 시 정원이 정확히 1회만 반환된다
- 전체관리자가 플랫폼 전체 매출·수수료를 하나의 대시보드에서 확인할 수 있다
- 회원은 취향 기반 맞춤 추천 박람회를 조회할 수 있다
- AI 기능(검색·추천·일정·요약·초안)이 실패해도 예약·결제·체크인 등 핵심 흐름은 막히지 않는다

## 4. 업무 규칙

| 업무 규칙 | 검증 가능한 결과 | 관련 시나리오 |
| --- | --- | --- |
| 로그인/권한 규칙 | 역할은 회원·주최자·전체관리자 세 가지다. 전체관리자 계정은 시스템 초기화 시 1건이 미리 생성되며, 초기 비밀번호는 어떤 문서·저장소에도 평문으로 기록하지 않는다(해시값을 환경변수로만 주입). 주최자 권한은 전체관리자가 계정을 직접 발급하거나 회원의 주최자 신청을 승인해 부여한다. 이미 주최자이거나 대기 중인 신청이 있는 회원은 다시 신청할 수 없고, 대기 중인 신청만 승인·거절할 수 있다. 로그인 실패는 가입 여부와 무관하게 같은 오류로 응답해 가입 여부가 드러나지 않는다. 회원은 실명과 닉네임을 따로 가진다 — 실명은 겹쳐도 되고 바꿀 수 없으며, 닉네임은 화면에 보이는 이름으로 유일해야 한다. 가입 시 닉네임은 실명으로 시작하되 이미 쓰이면 뒤에 “#숫자”를 붙인다. 구글·네이버·카카오 소셜 로그인은 처음 들어온 소셜 계정을 같은 이메일 회원에 연결하거나 새 회원(USER)으로 만들며, 한 소셜 계정은 한 회원에만 연결된다. 이메일로 기존 회원에 연결하는 것은 제공자가 검증한 이메일일 때만이다 — 구글은 토큰이 우리 앱에 발급된 것인지와 이메일 검증 여부를 확인하고, 카카오는 검증되지 않은 이메일이면 카카오 식별자로 만든 대체 이메일을 쓴다. 대체 이메일 형식으로는 직접 가입할 수 없다. 소셜로 가입한 회원은 비밀번호가 없어 이메일 로그인·비밀번호 변경을 쓸 수 없다. 소셜 로그인은 매번 제공자의 계정 확인 화면을 거치고, 제공자 응답을 기다리는 동안 DB 연결을 잡지 않으며 2~3초 안에 응답이 없으면 실패로 처리한다. | #1, #4 |
| 채널(테넌트) 격리 규칙 | 채널명 중복 생성이 거절된다. 한 주최자는 채널을 하나만 소유하며, 이미 채널이 있는 주최자의 추가 생성은 거절된다. 주최자는 자신의 채널 데이터에만 접근·수정할 수 있다. | #1, #8, #9 |
| 정원 관리 규칙 | 정원은 1명 이상이어야 하며, 잔여 정원을 초과하는 예약은 거절된다. 한 번에 예약할 수 있는 인원은 1~7명이다. 취소·만료·결제 실패 시 정원은 정확히 1회만 반환된다. 회차 시작 시각은 등록 시점보다 미래여야 하며, 종료 시각은 시작 시각보다 늦어야 한다. | #2, #3, #5, #6 |
| 회차 수정·삭제 규칙 | 회차에 유효한 예약(결제대기·확정)이 한 건이라도 있으면 일정·정원·참가비를 수정하거나 회차를 삭제할 수 없다. 회차 시작 시각이 지난 뒤에는 수정·삭제할 수 없다. 삭제한 회차는 목록과 예약 화면에서 사라지고 새 예약·수정을 받지 않지만(없는 회차로 취급), 지난 예약 이력은 그대로 보존된다. 참가비를 바꿔도 이미 만들어진 예약의 결제 금액은 변하지 않는다. 마지막 회차 삭제는 회차 삭제를 먼저 하고 박람회 숨김을 나중에 하며, 숨김이 실패하면 삭제도 되돌린다. | #9 |
| 공개 상태 관리 규칙 | 주최자만 자신의 박람회를 숨김 → 공개로 전환할 수 있으며, 회차가 하나도 없으면 공개할 수 없다. 공개 → 숨김 수동 전환은 제공하지 않으며, 공개 상태인 박람회의 마지막 회차가 삭제될 때만 시스템이 자동으로 숨김으로 전환한다. 공개 → 마감은 모든 회차 종료 시각이 지나면 시스템이 자동으로(10분 주기, 대상이 많아도 끝까지 훑음) 전환하며, 마감에서 다른 상태로 되돌아갈 수 없고 마감된 박람회는 수정할 수 없다. | #2, #9 |
| 공개 상태 조회 규칙 | 방문자·회원은 공개 상태인 박람회만 목록·상세에서 조회할 수 있다. 단 주최자는 자신의 채널에 속한 박람회라면 숨김·마감 상태도 조회할 수 있다. | #3, #9 |
| 예약 상태 전이 규칙 | 예약은 결제대기(Pending) → 확정(Confirmed) / 취소(Cancelled) / 만료(Expired)로만 전이하며 역행은 없다. 예약은 공개된 박람회의 시작 전 회차에만 신청할 수 있다. 참가비가 0원인 회차는 결제 없이 즉시 확정된다. 결제 실패는 취소, 10분 내 미결제는 만료로 구분해 사용자에게 사유를 표시하며, 만료 처리 전에 PG에 결제 여부를 다시 확인해 결제된 예약은 확정한다. 결제대기 예약을 취소할 때는 먼저 PG에 결제 여부를 확인해, 이미 결제됐으면 환불한 뒤 취소한다. 확정된 예약은 사용자 취소로 취소가 될 수 있으나, 이미 현장 입장(체크인)이 완료된 예약은 제외한다. 동일 회차에 유효한 예약이 이미 있는 회원의 추가 예약은 거절되며, 이 제약은 DB 가 보장해 동시 요청에서도 한 건만 생긴다. 취소·만료된 예약은 재예약을 막지 않는다. | #5, #6 |
| QR 발급·체크인 규칙 | QR 상태는 발급(ISSUED)·사용(USED)·무효(CANCELLED) 세 가지다. QR은 예약당 1건 발급되며 예약 인원 전체의 입장에 쓰인다. 확정 예약만 체크인 가능하고 동일 예약은 1회만 체크인된다. 체크인은 회차 시작 1시간 전부터 회차 종료 시각까지만 가능하며, 그 밖의 시각에는 거절하고 언제부터 가능한지 안내한다. 회차 시각을 확인할 수 없을 때는 시간창 검증만 건너뛰고 체크인을 허용한다. 티켓은 발급 직전에 예약이 여전히 확정 상태인지 확인해, 그사이 취소된 예약에는 발급하지 않는다. 예약이 취소되면 환불 여부와 무관하게 QR이 무효화된다. 같은 티켓의 체크인·되돌리기는 한 번에 하나씩만 처리돼 동시에 찍어도 한 번만 성공한다. 잘못 처리한 체크인은 주최자가 되돌릴 수 있다. 체크인과 되돌리기에는 처리자·처리 시각·처리 방법(QR/예약번호)이 기록되며, 이력과 추천 이벤트는 체크인이 확정된 뒤에만 남긴다. 체크인 조회·확정·되돌리기는 티켓을 찾기 전에 주최자 역할을 먼저 확인해, 주최자가 아니면 QR·예약번호의 존재 여부가 드러나지 않는다. | #5, #7 |
| 본인 예약 정보 조회 규칙 | 회원은 본인이 신청한 예약만 조회·취소할 수 있으며, 타인의 예약은 존재 여부도 알 수 없다. | #6 |
| 예약 취소 가능 기간 규칙 | 회차 시작 시각이 지난 예약은 취소할 수 없다. 이미 현장 입장(체크인)이 완료된 예약도 취소·환불할 수 없다. 입장 여부를 확인할 수 없는 경우에도 취소를 거절한다. | #6 |
| 환불 규칙 | 취소는 회차 시작 시각 전까지 가능하고, 환불은 회차 시작 시각 24시간 전까지 취소한 경우에만 전액 이뤄지며 그 이후에는 환불되지 않는다. 환불 처리가 실패해도 예약 취소는 되돌아가지 않으며 환불만 1분 주기로 최대 6회(간격 점증) 재시도하고, 끝내 실패하면 “환불 미해결”로 표시한다. | #6 |
| VIP 배너 노출 규칙 | 주최자는 자신의 공개 중인 박람회 단위로 추천 노출을 신청하고 9,900원을 결제할 수 있다. 숨김·마감 박람회는 신청할 수 없다. 배너는 서버가 PG에 결제 사실과 금액을 직접 확인한 뒤에만 켜지며, 확인 즉시 홈 상단 배너와 AI 추천순 맨 앞에 노출된다. 동시에 노출되는 배너는 최대 10개이며, 신청 때와 켜는 때 두 번 확인해 초과면 신청은 거절하고 켜는 단계면 결제를 환불하고 배너를 내린다. 배너 재신청으로 이전 결제대기 건을 정리할 때는 PG에 결제 여부를 확인해 결제됐으면 환불한다. 주최자가 환불하면 배너는 즉시 내려가고, 환불이 실패하면 예약 환불과 같은 방식으로 재시도한다. 노출 목록은 30초 단위로 순환한다. 박람회가 숨김·마감되면 노출 목록에서 즉시 빠지고, 결제일로부터 30일이 지나거나 마감된 배너는 매일 자정 만료 처리된다. | #10 |
| PG 키 보안 규칙 | PG 연동키(Secret)는 어떤 문서·저장소에도 평문으로 기록하지 않는다. 연동키는 서버 환경변수로만 주입하며, 화면에서 입력·조회하는 경로를 두지 않는다. | #5, #10 |
| PG 연동 방식 규칙 | PortOne 테스트 채널 키로 실제 PortOne API 를 호출해 결제·취소를 검증한다(로컬 개발은 Mock). 운영 전환 시 API 키만 교체하면 되도록 설계한다. 예약 결제와 배너 결제 모두 서버가 PG에 결제를 직접 확인하고, 결제 확인·PG 웹훅·만료 배치 세 경로가 같은 확인 함수를 탄다. 웹훅은 서명을 검증하고, 같은 웹훅은 한 번만 처리하되 결제 결과를 알 수 없었던 웹훅은 처리 완료로 기록하지 않아 재전송 시 다시 처리한다. | #5, #6, #10 |
| 정산 집계 규칙 | 전체관리자만 조회할 수 있다. 매출은 결제 완료 시각, 환불 차감은 환불 완료 시각이 속한 기간에 각각 집계한다. 지난 기간의 매출은 이후 환불이 발생해도 소급 수정하지 않으며, 환불은 발생한 기간의 차감 항목으로 잡는다. 결제된 적 없이 취소된 건은 환불로 보지 않고, 환불이 실패해 재시도 중인 결제는 환불이 끝날 때까지 매출로 남는다. 기간은 시작 시각을 포함하고 끝 시각은 포함하지 않는다. 플랫폼 수수료는 순매출(매출 − 환불)의 10%로 계산한다. 매출은 박람회 예약과 VIP 배너로 나눠 보여준다. | #11 |
| AI 추천 규칙 | 회원은 가입 시 또는 마이페이지에서 관심 분야(최대 6개)와 키워드(최대 30개)를 등록할 수 있다. 박람회가 공개되거나 공개 중 제목·소개문이 바뀌면 LLM 이 태그(최대 5개)를 만들고, 실패하면 분야별 기본 태그로 대체한다. 취향 점수는 태그 단위로 산정한다 — 체크인 5점, 예약 확정 4점, 상세 조회 0.5점에 30일 반감 recency decay 를 적용하고, 관심 분야 태그 3점·관심 키워드 2점은 감쇠 없이 더한다. 추천 목록은 공개 박람회 중 회원의 태그 점수 합이 높은 순으로 제공하며, 이미 예약한 박람회는 제외한다. 행동·관심사가 없는 회원에게는 추천 목록을 비워 보여준다. 박람회 상세에서는 태그를 공유하는 유사 박람회를 보여준다. recommendation-service가 죽거나 응답이 늦어도 예약·체크인 등 핵심 기능에 영향을 주지 않는다(fail-open). | AI-1 |
| 행동 데이터 수집 규칙 | 예약 확정(Reservation-Service)·체크인(Ticket-Service) 시 POST /internal/v1/recommendations/events 로, 로그인 회원의 박람회 상세 조회는 화면에서 recommendation-service 로 행동 이벤트를 전달한다. 같은 회원·박람회·이벤트 종류는 한 번만 기록한다. 이벤트 전달 실패는 fail-open 으로 처리하며 핵심 기능(예약·체크인)을 막지 않는다. 이번 Release 는 별도 동의 절차 없이 로그인 회원의 행동을 수집하며, 동의 화면은 후속 과제로 둔다. | AI-1 |
| 알림 규칙 | 알림은 두 종류다. 예약 확정 알림은 예약이 확정될 때 고정 문구로 예약당 1회 생성된다. 추천 알림은 매일 09시 배치가 공개 박람회의 태그에 대한 점수가 1점을 넘는 회원을 골라 생성하며, LLM 이 박람회별 한 줄 문구(60자 이내)를 만들고 실패하면 기본 문구를 쓴다. 대상 회원이 없으면 LLM 을 호출하지 않는다. 같은 박람회 추천 알림은 회원당 1회만 보낸다. 알림은 개별·전체 읽음 처리가 가능하며, 읽지 않은 수를 헤더 종 아이콘 뱃지로 표시한다. 알림 발송 실패는 fail-open 으로 처리한다. | AI-1, #5 |
| AI 일정 추천 규칙 | 회원은 캘린더 화면에서 보고 있는 달을 기간으로, 자연어 조건(최대 200자, 예: 오후 2시 이후 IT 행사)을 입력할 수 있다. LLM 은 조건에서 시작 가능 시각과 분야만 추출한다. 공개 박람회의 시작 전 회차 중 조건을 만족하는 회차를 종료 시각이 이른 순으로 서로 겹치지 않게 고르며, 한 박람회에서는 한 회차만 고른다. LLM 호출이 실패하면 “오전/오후 N시 이후” 규칙 해석으로, 그것도 안 되면 조건 없이 배치한다(fail-open). 추천 결과는 저장하지 않고 요청마다 계산한다. 회원당 분당 5회까지 요청할 수 있다. | AI-2 |
| 체크인 결과 요약 규칙 | 주최자는 자기 박람회의 결과만 볼 수 있다(타인 박람회·주최자 외 역할은 403). 수치는 체크인 이력을 규칙으로 집계하고 LLM 은 문장화에만 쓴다 — LLM 이 수치를 만들지 않는다. 입장 기록이 0건이면 LLM 을 호출하지 않는다. LLM 실패·키 없음·호출 한도 초과 시 요약만 비우고 수치는 표시한다(fail-open). 예약 수를 가져오지 못하면 예약·노쇼·입장률은 0 으로 두고 입장 수는 표시한다. | AI-3 |
| 자연어 검색 규칙 | 검색 문장은 최대 200자다. LLM 은 문장을 지역·분야·유료/무료·기간·키워드 조건으로 바꾸기만 하고, 박람회 목록은 DB 가 그 조건으로 조회한다 — LLM 이 목록을 만들지 않는다. 지역은 실제 공개 박람회에 쓰인 지역, 분야는 6개 분야 중 하나일 때만 인정하고 나머지는 버린다. “박람회·전시회·행사” 같은 일반어는 키워드에서 뺀다. 키워드는 제목·소개문·장소에서 찾는다. 기간은 한국 시간 기준 최대 90일이며, 기간 안에 예약 가능한 회차가 있는 박람회만 남긴다. LLM 호출이 실패하면 문장 전체를 키워드로 검색한다(fail-open). 기간 조건 확인에 필요한 회차 조회가 실패하면 틀린 결과 대신 503 을 돌려준다(fail-closed). 유료 여부를 확인할 수 없는 박람회는 유료/무료 조건에서 제외하지 않는다. | AI-4 |
| 소개글 초안 규칙 | 주최자는 자기 채널에서만 초안을 요청할 수 있다. 키워드는 1~10개, 각 50자 이내이며, 초안은 최대 600자다. 초안은 응답으로만 돌려주고 저장하지 않으며, 주최자가 읽고 저장해야 박람회에 반영된다. 이미 작성한 소개글이 있으면 덮어쓰기 전에 확인한다. LLM 호출이 실패하면 초안 없이 기존 입력을 그대로 둔다. | AI-5 |
| 정산 AI 요약 규칙 | 기간별 수치와 환불 이상치(환불이 구간 평균 + 2σ 를 넘는 구간, 3개 구간 이상일 때만 판단)는 규칙으로 계산하고, LLM 은 이를 2문장으로 요약하는 데만 쓴다. LLM 호출이 실패하면 요약만 비우고 대시보드 수치는 그대로 표시한다(fail-open). | AI-6 |
| AI 호출 공통 규칙 | 모든 LLM 호출은 common-ai 모듈을 거친다. LLM 은 조건 해석과 문장 작성에만 쓰고, 목록·수치는 DB 와 규칙이 만든다. 서비스별 하루 호출 한도(기본 1,000회)를 넘으면 호출하지 않고 폴백한다. 같은 입력은 캐시(기본 6시간)로 재사용한다. 5xx·429 는 잠시 기다렸다가 재시도하고, 그 밖의 4xx 와 타임아웃은 즉시 포기한다. 실패는 예외 대신 null 을 반환해 각 기능이 폴백하게 한다. API 키는 요청 헤더(x-goog-api-key)로만 보내고 로그·URL 에 남기지 않는다. | AI-1 ~ AI-6 |

## 5. 업무 용어

| 업무 용어 | 제품에서 사용하는 의미 |
| --- | --- |
| 채널 | 주최자가 소유하는 박람회 묶음 단위. 서로 다른 채널의 데이터는 격리된다. 한 주최자는 채널을 하나만 소유한다 |
| 박람회 | 채널에 속한 행사 단위. 이름·소개문·대표 이미지·상세 이미지·장소·지역·분야·공개 여부를 가진다 |
| 분야 | 박람회 분류. IT·전자, 식품·음료, 패션·뷰티, 교육·취업, 문화·예술, 기타 6가지 |
| 회차 | 박람회 안에서 시작·종료 시각과 정원·참가비를 가진 참관 단위 |
| 정원 / 잔여 정원 | 한 회차가 수용할 수 있는 최대 확정 인원 수 / 정원에서 확정 예약 인원과 결제 대기 중인 인원을 뺀 값 |
| 결제대기(Pending) | 정원이 임시로 확보되었으나 결제가 완료되지 않아 아직 확정되지 않은 예약 상태 |
| 확정 / 취소 / 만료 | 정원이 확보되어 참관이 보장된 예약 상태 / 참관을 철회하거나 결제에 실패해 정원이 반환된 예약 상태 / 결제대기 시간이 지나 자동으로 정리되고 정원이 반환된 예약 상태 |
| 예약자 연락처 | 예약 시점에 입력받아 예약에 함께 보관하는 이름과 전화번호 |
| 체크인 토큰 | QR 티켓에 담기는 불투명 검증 값 |
| 예약번호 | 회원에게 보여주는 예약 식별자. QR을 쓸 수 없을 때 현장에서 수동 입력으로 체크인하는 데 쓴다 |
| 실명 / 닉네임 | 가입 때 입력한 이름(겹쳐도 됨, 변경 불가) / 화면에 보이는 유일한 이름(변경 가능, 중복 시 “#숫자”) |
| 주최자 신청 | 회원이 주최자 권한을 요청하는 절차. 대기 → 승인 / 거절로 처리된다 |
| 소셜 계정 연결 | 구글·네이버·카카오 계정을 플랫폼 회원 한 명에 묶어 두는 것. 같은 소셜 계정은 두 회원에 연결될 수 없다 |
| VIP 배너 | 주최자가 결제해 30일간 홈 상단 배너와 AI 추천순 맨 앞에 노출하는 추천 노출 상품 |
| 정산 | 플랫폼 전체 매출에서 환불을 빼고 수수료를 산출해 기간별로 집계하는 절차 |
| 숨김 / 공개 / 마감 | 박람회의 노출 상태 |
| 태그 | 박람회 공개 시 LLM 이 제목·소개문으로 만든 키워드(최대 5개). 추천·유사 박람회 매칭에 쓴다 |
| 취향 점수 | 회원의 행동 데이터와 관심사를 기반으로 태그별로 산정한 선호도 수치. 행동 점수에 30일 반감 recency decay 적용 |
| 행동 이벤트 | 회원이 플랫폼에서 수행한 행동(박람회 조회·예약 확정·체크인)의 기록. AI 추천에 활용된다 |
| 개인화 알림 | recommendation-service가 취향 점수와 추천 결과를 기반으로 회원에게 발송하는 맞춤형 알림 |
| 조건 칩 | 자연어 검색에서 AI 가 해석한 조건(지역·분야·유료/무료·기간·키워드)을 보여주는 표시. 지우면 그 조건을 빼고 다시 검색한다 |
| 폴백(fail-open) | AI 호출이 실패했을 때 오류 대신 AI 없는 기본 동작(키워드 검색·기본 문구·수치만 표시 등)으로 대체하는 것 |

## 6. 미결 사항

| 항목 | 해소 |
| --- | --- |
| 취소 기한과 환불 기한을 하나로 통일할지 | 의도한 정책대로 이행(취소와 환불 기한 분리) |
| QR 발급 단위 | 예약당 1건 발급, reservation_id UNIQUE로 멱등 보장 |
| 환불 재시도 주체·주기 | common-payment 배치, 1분 주기·6회 포기 |
| 이미 체크인한 예약의 취소·환불 허용 여부 | 허용하지 않음 |
| 주최자가 공개된 박람회를 직접 숨김으로 되돌릴 수 있는가 | 이번 Release 에서는 제공하지 않음. 마지막 회차 삭제 시 자동 숨김만 지원하고, 수동 전환은 후속 백로그로 이동 |
| 예약 확정 이메일 통지를 이번 Release에 넣을지 | 이메일 대신 앱 내 알림(헤더 종 아이콘)으로 대체 — 예약 확정 시 알림 생성, 읽지 않은 수 뱃지 |
| AI 행동 데이터 수집 동의 체계 | 이번 Release 는 별도 동의 절차 없이 로그인 회원의 행동을 수집. 동의 화면은 후속 백로그로 이동 |
| LLM 호출 실패 시 expo_tags 공백 허용 여부 | 공백을 허용하지 않고 분야별 기본 태그로 대체 |
| AI가 추천한 일정을 저장할지 | 저장하지 않고 요청마다 계산(테이블·ERD 변경 없음) |
| PG 연동키를 화면에서 등록·관리할지 | 이번 Release 는 서버 환경변수로만 주입. 암호화 저장·마스킹 조회 화면은 후속 백로그로 이동 |
| 중복 예약을 서비스 검사로 막을지 DB 제약으로 막을지 | DB 제약으로 보장. 유효 예약일 때만 값이 생기는 컬럼에 UNIQUE 를 걸어 취소 후 재예약은 허용 |
| VIP 배너 결제를 웹훅만으로 켤지 | 예약 결제와 같게 서버가 PG에 직접 확인하는 경로를 기본으로 하고, 웹훅은 서명 검증 후 보조로 처리 |
