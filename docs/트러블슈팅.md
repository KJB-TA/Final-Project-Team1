## 1. 결제·정산

### #1 지난달 매출이 환불 시점에 소급해서 사라짐

- **증상**: 9월에 결제하고 10월에 환불하면 9월 매출에서 그 건이 사라지고 10월에는 환불만 잡혔다. 같은 달에 결제·환불된 건은 매출 없이 환불만 잡혀 순매출이 음수가 됐다. 결제된 적 없는 취소는 환불로 잡히고, 환불 재시도 중인 건은 매출에서 빠졌다.
- **원인**: 정산이 결제를 `updatedAt` 과 **현재 상태**(`PAID`·`CANCELLED`)로 조회했다. 환불되면 상태와 `updatedAt` 이 함께 바뀌므로 원래 결제 기간에서 빠진다. 정산은 "그 기간에 무슨 일이 있었나" 를 묻는데, 상태는 "지금 어떤가" 만 답한다.
- **해결**: 결제 1건을 결제 사건(`paid_at`)과 환불 사건(`cancelled_at`) 두 시각으로 본다. 내부 조회는 둘 중 하나가 `[from, to)` 에 든 결제만 돌려주고(결제된 적 없는 건 제외), 매출은 `paid_at`, 환불은 `cancelled_at` 이 기간 안일 때만 센다. 합계·달력·랭킹이 같은 기준을 쓰고, 반열린 구간이라 경계 시각이 두 기간에 겹쳐 잡히지 않는다. 배너 결제 응답에도 `cancelledAt` 을 추가했다.
- **검증**: `SettlementServiceTest`, `GetPaymentsForSettlementTest`, `InternalPromotionPaymentApiTest` 보강.
- **배운 점**: 집계는 상태가 아니라 사건 시각으로 한다. 상태는 덮어써지지만 사건 시각은 남는다.
- **근거**: PR #320 (`da1a73f`)

### #11 결과를 모르는 웹훅을 "처리 완료" 로 기록해 재전송이 무시됨

- **증상**: PG 가 일시적으로 응답하지 않을 때 웹훅이 오면, 서버는 503 으로 재전송을 요청하면서도 이벤트를 처리 완료로 기록했다. PortOne 이 다시 보내면 중복으로 무시돼, 결제는 됐는데 예약은 결제 대기로 남았다. 만료 배치의 PG 재조회만이 이를 정리했다.
- **원인**: `WebhookService` 가 PG 조회 결과와 상관없이 `markProcessed()` 를 호출했다. "다시 보내 달라" 는 응답과 "이미 처리했다" 는 기록이 서로 모순이었다.
- **해결**: 결과가 `UNKNOWN` 이면 이벤트를 `RECEIVED` 로 남긴다. 같은 `webhook-id` 로 재전송이 오면 `RECEIVED` 건은 다시 처리하고, 처리 완료 건만 중복으로 거른다.
- **검증**: `WebhookServiceTest` 3종 — 결과 모름이면 `RECEIVED` 유지, `RECEIVED` 건 재전송은 재확인 후 완료, 완료 건 재전송은 PG 를 다시 조회하지 않음.
- **배운 점**: 멱등성 기록은 "끝까지 성공했을 때" 만 남긴다. 실패까지 기록하면 재시도 장치가 스스로를 막는다.
- **근거**: PR #321 (`5fa24ff`)

### #21 운영이 모의 PG 로 결제를 무조건 성공 처리 — 실결제 시험에서 버그 2건 추가 발견

- **증상**: 운영 expo·reservation 서비스가 `prod` 프로필로만 떠서 `MockPgClient` 가 주입됐다. PG 에 묻지 않고 항상 결제 성공으로 보기 때문에, 결제창을 닫거나 결제가 실패해도 예약이 확정될 수 있었다.
- **원인**: 실제 PG 클라이언트(`PortOneClient`)는 `@Profile("portone-live")` 에만 등록되는데, 운영 compose 가 이 프로필을 켜지 않았다. 코드가 아니라 배포 설정의 누락이라 테스트로는 드러나지 않았다.
- **해결**: 운영 compose 에서 두 서비스를 `prod,portone-live` 로 띄운다(`PAYMENT_SERVICE_PROFILES`). 문제가 생기면 서버 `.env` 한 줄로 즉시 모의 결제로 되돌릴 수 있다. 전환 전에 로컬에서 실제 PortOne 테스트 채널로 결제·취소를 끝까지 돌려, 모의 결제로는 보이지 않던 버그 2건을 더 찾아 고쳤다.
  1. **승인은 됐는데 예약이 확정되지 않음**: PortOne 은 성공 응답에 PG 원본 JSON(1,517자)을 담아 준다. 이를 `pg_response_code`(VARCHAR 50)에 저장하다 실패해 확정 트랜잭션 전체가 롤백됐다. → 상태값만 저장하고, 길이를 넘는 값은 잘라서 담는다.
  2. **환불하지 않았는데 "환불 완료" 로 기록됨**: 사전등록과 취소가 같은 `Idempotency-Key`(결제 ID)를 썼다. PortOne 은 이미 쓴 키를 중복 요청으로 보고 앞선 사전등록 응답을 그대로 돌려줬다. → 취소는 `cancel-` 접두어를 붙인 별도 키를 쓰고, 응답에 취소 내역이 없으면 실패로 보아 환불 재시도 배치가 회수한다.

  | 실험 (PortOne 테스트 채널) | 응답 |
  | --- | --- |
  | 멱등 키 없이 취소 | `409 PAYMENT_ALREADY_CANCELLED` |
  | 사전등록과 같은 키로 취소 | `200 {}` — 취소는 실행되지 않음 |

- **검증**: 유료 예약 1건을 결제 → 확정 → 취소까지 진행하고, 우리 DB 와 PortOne 단건 조회를 대조했다(예약·결제 `CANCELLED`, PortOne 취소액 1,000원). QR 티켓 무효화와 예약 확정 알림도 확인했다. common-payment 회귀 테스트 4건 추가.
- **배운 점**: 모의 객체는 "항상 성공하는 PG" 라서 실패 경로와 외부 응답 형식을 검증하지 못한다. 운영과 같은 조건으로 한 번은 끝까지 돌려 봐야 한다. 멱등 키는 작업마다 따로 쓴다.
- **근거**: Issue #243, PR #244 (`855ab86`, `b1c0dd9`)

### #28 결제 직후 취소하면 돈은 받고 환불은 안 됨

- **증상**: 결제창에서 결제가 끝났는데 웹훅이나 확정 호출이 오기 전에 취소하면 환불 없이 취소됐다. 뒤늦게 온 웹훅은 이미 취소된 예약이라 409 로그만 남겼다. VIP 배너도 재신청할 때 이전 `PENDING` 배너를 PG 확인 없이 취소해 같은 일이 생겼다.
- **원인**: 취소 로직이 **로컬** 결제 상태(`PENDING`)만 보고 "돈을 받지 않았다" 고 판단했다. 로컬 상태는 PG 보다 늦게 바뀔 수 있다.
- **해결**: 만료 배치와 같은 방식으로, 취소 직전에 PG 를 조회해 결제 상태만 맞춘다(예약은 확정하지 않는다). PG 가 `PAID` 면 기존 환불 경로를 타고, 확정된 적 없는 예약이므로 환불 기한과 상관없이 전액 환불한다. PG 가 모르면(`UNKNOWN`) 지금처럼 환불 없이 취소한다. PortOne 은 결제창을 열었다 닫기만 한 결제도 `NOT_FOUND` 로 주기 때문에, 여기서 막으면(fail-closed) 결제창을 닫은 뒤의 취소가 전부 실패한다.
- **검증**: `ReservationCancelServiceTest` 2건 추가(`PENDING` 취소 + PG `PAID` 면 기한 안쪽이어도 `REFUNDED`, PG 모름이면 환불 없이 `CANCELLED`), `PromotionReapplyStalePendingTest` 2종. 수정 전 코드로는 `PAID` 케이스 두 건이 실패하는 것을 먼저 확인했다.
- **남은 한계**: 취소 **이후에** 결제가 완료되는 경우(다른 탭에서 결제를 계속 진행 등)는 범위 밖이다. 웹훅 쪽 보상 처리가 필요하다.
- **배운 점**: 돈에 관한 판단은 로컬 상태가 아니라 원장(PG)에 묻는다. "모를 때" 의 기본값은 경로마다 따로 정한다.
- **근거**: PR #326 (`75b9a89`)

### #30 배너 환불 실패가 롤백되며 재시도 기록까지 사라짐

- **증상**: ① PG 가 환불을 거절하면 결제만 `REFUND_FAILED` 가 되고 배너는 `ACTIVE` 로 남았다. 재시도 배치는 결제 행만 `CANCELLED` 로 바꾸므로, 환불이 끝난 뒤에도 배너가 계속 노출됐다. ② PG 통신이 실패하면 `markRefundFailed()` 직후 예외를 던져 트랜잭션이 롤백됐고, `REFUND_FAILED` 기록이 사라져 재시도 대상에서도 빠졌다.
- **원인**: 실패를 예외로 알리면서 동시에 기록으로도 남기려 했다. 같은 트랜잭션 안에서 던진 예외는 그 기록까지 되돌린다.
- **해결**: 예약 취소와 같은 순서로 맞췄다. 배너를 먼저 `CANCELLED` 로 내리고, PG 가 실패하면 예외 없이 `REFUND_FAILED` 로 기록해 재시도 배치에 맡긴다. 통신 실패 뒤 실제로는 PG 에서 취소됐더라도, 재시도할 때 PG 가 409(이미 취소됨)를 주면 성공으로 처리하므로 중복 환불은 생기지 않는다.
- **검증**: `PromotionRefundFailureTest` 2종 — PG 거절·통신 실패 모두 200, 배너 `CANCELLED`, 결제 `REFUND_FAILED` 가 롤백되지 않고 남음. 수정 전 코드로는 `ACTIVE`, `503` 으로 실패하는 것을 확인했다.
- **배운 점**: 재시도에 맡길 실패는 예외로 던지지 말고 커밋되는 상태로 남긴다. 배너 슬롯 초과 환불(#5·#10)도 같은 규칙을 따른다.
- **근거**: PR #325 (`d72be52`)

### #2 예약이 남은 마지막 회차를 지우면 삭제는 실패하고 박람회만 숨겨짐

- **증상**: 공개 박람회에 회차 1개·예약 1건이 있을 때 회차를 삭제하면 409 로 실패하는데, 박람회는 `HIDDEN` 으로 바뀌어 있었다.
- **원인**: 회차(reservation-service)와 박람회 상태(expo-service)는 소유 서비스가 다르고, HTTP 호출에는 원자성이 없다. 코드는 "비공개 먼저, 삭제 나중" 순서였다. 되돌릴 수 없는 원격 비공개가 성공한 뒤 로컬 삭제가 예약 때문에 실패하면 원래대로 돌릴 방법이 없었다.
- **해결**: 순서를 뒤집었다. 되돌릴 수 있는 로컬 삭제(예약이 0건일 때만 성공하는 조건부 UPDATE)를 먼저 하고, 성공했을 때만 원격 비공개를 요청한다. 비공개 요청이 실패하면 예외로 트랜잭션이 롤백돼 삭제도 되돌아간다. 조건부 UPDATE 가 행 잠금을 잡으므로 커밋 전까지 새 예약도 끼어들지 못한다.
- **검증**: `DeleteRoundServiceTest`. 이 결함은 Sprint 테스트로는 잡지 못했고 문서 대조에서 발견했다.
- **배운 점**: 서비스 경계를 넘는 두 쓰기는 "되돌릴 수 있는 로컬 → 되돌릴 수 없는 원격" 순서로 한다. Saga 없이도 실패했을 때 남는 상태를 줄이는 최소한의 규칙이다.
- **근거**: PR #320 (`cecad50`)

### #4 같은 회원이 같은 회차에 동시에 요청하면 유효 예약이 2건 생김

- **증상**: 예약 버튼을 더블클릭하면 `PENDING` 예약이 2건 생겼다.
- **원인**: 서비스가 "활성 예약이 있는지 보고(`exists`) → 없으면 저장" 순서였고, DB 제약도 락도 없었다. 두 요청이 동시에 `exists = false` 를 보고 둘 다 저장했다.
- **해결**: 방법을 비교했다. 회원·회차 단위 락은 아직 예약 행이 없어 잠글 대상이 없고, 일반 UNIQUE(`round_id`, `user_id`)는 취소 후 재예약까지 막는다. 그래서 **유효 상태일 때만 값이 생기는 STORED 생성 컬럼**에 UNIQUE 를 걸었다(V14).

  ```sql
  active_holder VARCHAR(64) GENERATED ALWAYS AS (
      CASE WHEN status IN ('PENDING', 'CONFIRMED') THEN CONCAT(round_id, ':', user_id) END) STORED,
  CONSTRAINT uk_reservations_active_holder UNIQUE (active_holder)
  ```

  취소·만료되면 값이 `NULL` 이 되고, MySQL UNIQUE 는 `NULL` 끼리는 막지 않으므로 재예약은 그대로 된다. 제약 위반은 제약 이름으로 구별해 409 `DUPLICATE_RESERVATION` 으로 바꾸고, 예외로 롤백되면서 먼저 차감한 정원도 되돌아간다.
- **검증**: `DuplicateReservationTest` 2건 추가 — 서비스를 거치지 않고 유효 예약 2건을 직접 INSERT 하면 DB 가 두 번째를 거절, 같은 회원의 동시 요청 2건은 하나만 성공하고 실패한 쪽 정원은 복귀. 같은 회원의 예약 2건을 픽스처로 쓰던 `ExpireIfPendingTest` 는 회원 2명으로 고쳤다.
- **운영 적용**: UNIQUE 를 추가할 때 기존 중복이 있으면 마이그레이션이 실패해 서비스가 뜨지 않는다. 배포 전에 중복 유효 예약 0건을 확인하는 절차를 두었고, 2026-09-27 배포 뒤 reservation-service 가 정상 기동하는 것으로 적용을 확인했다.
- **배운 점**: "검사 후 삽입" 은 동시 요청에서 반드시 샌다. 최종 방어선은 DB 제약이다.
- **근거**: PR #321 (`aa22e80`), `V14__unique_active_reservation_per_member.sql`

### #16 같은 QR 을 동시에 찍으면 모두 입장 성공

- **증상**: 스태프 여러 명이 같은 QR 을 거의 동시에 찍으면 모두 성공하고 체크인 이력도 여러 줄 남았다.
- **원인**: `checkin()` 이 티켓을 읽어 `ISSUED` 인지 확인하고 `USED` 로 바꾸는 사이에 락이 없었다. 동시 요청이 모두 `ISSUED` 를 읽고 통과했다.
- **해결**: 티켓을 `findByIdForUpdate()`(`PESSIMISTIC_WRITE`, `SELECT … FOR UPDATE`)로 읽는다. 두 번째 요청은 첫 번째가 커밋될 때까지 기다린 뒤 `USED` 를 보고 409 를 받는다. 조건부 UPDATE 대신 락을 고른 이유는 "이미 사용됨·취소된 티켓" 판단을 도메인 메서드 `Ticket.checkIn()` 에 그대로 두기 위해서다. 티켓 한 행만 잠그므로 다른 티켓의 체크인에는 영향이 없다. 되돌리기에도 같이 적용했다.
- **검증**: `CheckinConcurrencyTest` — 5명이 같은 티켓을 동시에 체크인하면 성공 1건, 상태 `USED`, 이력 1행(Testcontainers MySQL). 수정 전 코드로는 `expected: 1L but was: 5L` 로 실패하는 것을 확인했다.
- **배운 점**: 상태 전이 규칙을 엔티티에 두었다면, 그 엔티티를 읽는 순간부터 잠가야 동시 요청에서도 규칙이 지켜진다.
- **근거**: PR #324 (`e2c0357`)

### #29 취소된 예약에 티켓이 발급됨

- **증상**: 취소·환불까지 끝난 예약에 유효한 QR 티켓이 생길 수 있었다.
- **원인**: 세 단계가 겹쳤다. ① 예약 확정 순간 ticket-service 가 잠깐 죽어 있으면 발급(ISSUE) 통지가 재시도 대기로 남는다. ② 그 사이 사용자가 취소하면 무효화(REVOKE)가 먼저 실행되는데, 티켓이 아직 없으니 아무것도 하지 않고 성공한다. ③ 나중에 ISSUE 재시도가 성공하면 취소된 예약에 티켓이 생긴다. 발급 직전에 예약 상태를 확인하지 않았다.
- **해결**: ISSUE 를 보내기 직전에 예약을 `findByIdForUpdate()` 로 읽어, `CONFIRMED` 가 아니면 보내지 않고 통지를 `GAVE_UP` 으로 끝낸다. 잠그는 이유는 "확인 직후, 발급 직전" 에 끼어드는 취소까지 막기 위해서다. 발급하는 동안 들어온 취소(`cancelIfActive` UPDATE)는 발급 트랜잭션이 끝날 때까지 기다리고, 그 뒤 적재되는 REVOKE 가 방금 발급된 티켓을 무효화한다. 잠금은 예약 한 행에, 발급 호출 한 번 동안만 걸린다.
- **검증**: `TicketDispatchTest` 2건 추가 — 예약이 `CANCELLED` 면 ISSUE 를 보내지 않고 `GAVE_UP`, REVOKE 는 상태를 조회하지 않고 그대로 보냄. 상태 확인 줄을 끄면 새 테스트가 실패하는 것을 확인했다.
- **배운 점**: 재시도 큐의 작업은 "만들어질 때" 가 아니라 "실행될 때" 의 상태로 판단한다.
- **근거**: PR #327 (`2466e8f`)

### #31 자동 마감이 앞쪽 500개에서 멈춤

- **증상**: 이미 마감된 박람회가 500개(조회 한도)를 넘으면, 새로 끝난 박람회가 `CLOSED` 로 바뀌지 않았다.
- **원인**: 마감 대상을 주는 내부 API `finished-expos` 는 박람회 상태를 모르는 reservation-service 에 있어서, 이미 `CLOSED` 인 박람회도 id 순으로 최대 한도만큼 돌려줬다. 스케줄러는 매번 같은 앞쪽 페이지만 처리했다.
- **해결**: 내부 API 에 `afterExpoId` 커서를 추가하고(기본값 0 이라 기존 호출과 호환), 스케줄러는 빈 페이지가 나올 때까지 훑는다(#328). 이어서 커서를 모르는 옛 reservation-service 와 섞여 배포되면 같은 페이지가 계속 돌아와 루프가 끝나지 않고, 스케줄러 스레드를 붙잡아 배너 만료·환불 재시도까지 멈출 수 있다는 점을 발견했다. 그래서 커서가 전진하지 않으면 경고를 남기고 끝낸다(#329).
- **검증**: `ExpoAutoCloseSchedulerTest` — 한도 2에 대상 3개면 두 번째 페이지까지 조회해 세 번째도 `CLOSED`, 같은 페이지만 돌려주는 상황에서도 10초 안에 종료. 수정 전 코드는 시간 초과로 실패했다.
- **배운 점**: 페이지 반복에는 "진행하지 않으면 멈춘다" 를 종료 조건에 넣는다. 서비스 간 API 를 바꿀 때는 옛 버전과 섞여 배포되는 순간까지 고려한다.
- **근거**: PR #328 (`2f9b7a4`), PR #329 (`72da4e0`)

## 3. 보안·인가

### #5·#10 결제 확인 없이 VIP 배너를 켤 수 있었음

- **증상**: ① 배너 웹훅에 서명 검증이 없었고, **화면이 그 웹훅을 직접 호출해 배너를 켜고 있었다.** 결제하지 않은 요청으로도 배너를 켤 수 있는 구조였고, 금액 검증도 없었다. ② PG 재조회가 실패하면 `IGNORED` 로 기록돼 PortOne 재전송도 중복으로 무시됐고, 결제는 됐는데 배너는 계속 `PENDING` 이었다. ③ 숨김·마감 박람회도 배너를 신청할 수 있었고, 숨긴 박람회가 배너 노출에서 빠지지 않았다(#5).
- **원인**: 예약 결제는 common-payment 의 서명 검증·PG 재조회 경로를 탔지만, 배너는 따로 만든 웹훅 서비스(`ExpoPromotionWebhookService`)가 그 경로를 거치지 않았다. 같은 기능을 두 번 구현하면서 한쪽에만 검증이 빠졌다.
- **해결**: 배너 웹훅을 common-payment `WebhookService`(Webhook Secret 서명 검증)로 합치고 별도 서비스는 삭제했다. 화면은 새 `POST /api/v1/expo-promotions/{id}/payment` 를 부르고, 서버가 PG 에 직접 조회해 금액까지 확인한 뒤에만 `ACTIVE` 로 켠다. 신청 시 `PUBLISHED` 인지 검사하고, 배너 목록은 조회 시점에 비공개 박람회를 바로 뺀다(자정 만료 배치를 기다리지 않는다). 후속으로 `ACTIVE` 로 켜는 순간 슬롯 수를 다시 세고, 가득 찼으면 방금 받은 결제를 환불하고 `CANCELLED` 로 내린다(#328).
- **검증**: `ExpoPromotionApiTest` 6건 추가(비공개 박람회 신청 409, 결제 확인 정상·두 번·타인, 서명이 틀리거나 없는 웹훅은 401/400 에 상태 불변), `ActivePromotionApiTest`, `PromotionSlotOnActivationTest`.
- **남은 한계**: 마지막 한 자리에 결제 확정 두 건이 정확히 동시에 들어오면 둘 다 켜질 수 있다. 잠글 슬롯 행이 없기 때문이다.
- **배운 점**: 결제 확정은 반드시 서버가 PG 에 직접 묻는다. 클라이언트가 "결제됐다" 고 알리는 경로는 믿지 않는다. 결제 경로는 하나로 모은다.
- **근거**: PR #321 (`1365205`), PR #328 (`c80c3d1`)

### #12 응답 코드 차이로 예약번호·QR 존재 여부가 드러남

- **증상**: 일반 회원 토큰으로 `GET /api/v1/tickets/verify?reservationNo=` 를 부르면, 없는 번호는 404, 있는 번호는 403 이 나왔다. 응답 차이만으로 예약번호·QR 이 존재하는지 알아낼 수 있었다.
- **원인**: 티켓을 먼저 찾고(없으면 404), 그 뒤에 역할·소유권을 확인(403)했다.
- **해결**: 조회·체크인·되돌리기 모두 **역할 확인을 맨 앞으로** 옮겼다. 주최자가 아니면 티켓 존재 여부와 상관없이 403 이다.
- **검증**: `TicketCheckinServiceTest` 3건 추가 — 회원 토큰으로 없는 코드·예약번호·티켓 id 를 보내면 404 가 아니라 403.
- **배운 점**: 인가 검사는 리소스 조회보다 먼저 한다. 오류 코드의 차이도 정보 노출이다. 로그인도 같은 원칙으로, 없는 이메일과 틀린 비밀번호의 응답 본문과 응답 시간을 같게 만들었다(없는 이메일도 더미 해시와 한 번 비교).
- **근거**: PR #321 (`2e4f847`)

### #22 만료 토큰이 남아 있으면 로그인까지 막힘

- **증상**: 브라우저에 만료된 토큰이 남아 있으면 로그인·회원가입처럼 인증이 필요 없는 요청까지 401 로 막혔다. `/api/v1/expo-promotions`(VIP 배너 신청), `/api/v1/tickets` 처럼 하위 경로가 없는 요청은 라우팅되지 않았다.
- **원인**: ① `JwtAuthenticationFilter` 가 무효 토큰이 붙은 요청을 즉시 401 로 끊었다. "토큰이 틀렸다" 와 "이 요청은 인증이 필요하다" 를 한곳에서 판단한 것이다. ② nginx `location` 에 후행 슬래시(`/api/v1/tickets/`)가 붙어 있어, 슬래시 없이 끝나는 요청이 매칭되지 않았다.
- **해결**: 필터는 무효 토큰을 **헤더가 없는 것과 똑같이** 통과시키고, 보호가 필요한 기능이 `AuthContext` 유무를 직접 검사해 거절한다. 프론트 `apiFetch` 는 401 + `data.code == UNAUTHENTICATED` 이면 저장된 토큰을 지우고 로그인 화면으로 보낸다. nginx `location` 도 고쳤다. 이후 정산 API 가 이 형식을 따르지 않아 관리자 토큰 만료 시 알 수 없는 오류만 뜨던 문제도 같은 형식으로 맞췄다(#329).
- **검증**: `TokenRejectionTest`
- **배운 점**: 인증(누구인가)과 인가(허용되는가)를 분리한다. 공통 필터는 신원만 세우고, 거절은 기능이 한다. 서비스 여섯 개가 같은 규칙을 쓰도록 이 필터를 공통 모듈(`common-security`)에 두었다.
- **근거**: PR #151 (`13ab3b9`), PR #329

### #25 다른 앱이 받은 구글 토큰으로 우리 서비스에 로그인할 수 있었음

- **증상**: 코드 리뷰에서 발견했고, 실제 피해는 없었다. 구글 로그인이 받은 액세스 토큰으로 userinfo 만 조회했다. userinfo 는 **어느 앱이 받은 토큰이든** 응답하므로, 피해자가 다른 사이트에서 구글 로그인을 하면 그 사이트가 받은 토큰으로 우리 서비스에 피해자로 로그인할 수 있었다. 같은 이메일의 기존 계정(비밀번호 계정·주최자 계정 포함)에 자동 연결되므로 구글로 가입한 적 없는 회원도 대상이었다. 함께 발견한 것은 다음과 같다.
  - 제공자가 소유를 확인하지 않은 이메일로도 기존 회원에 연결됨
  - 카카오 대체 이메일(`kakao_{id}@social.expohub.local`)로 먼저 일반 가입해 두면, 그 카카오 계정의 첫 로그인이 선점한 계정에 연결됨
  - 카카오 인가 요청에 `state` 가 없어 로그인 CSRF 가능, 네이버 `state` 는 `Math.random` 기반
- **원인**: "토큰이 유효하다" 와 "토큰이 우리 앱에 발급됐다" 를 구분하지 않았다(OAuth 의 audience 확인 누락). 이메일을 계정 연결 키로 쓰면서 이메일의 검증 여부를 보지 않았다.
- **해결**: userinfo 조회 전에 tokeninfo 로 `aud == GOOGLE_CLIENT_ID` 를 확인하고, Client ID 가 설정되지 않았으면 모든 토큰을 거절한다(fail-closed). 구글은 `verified_email`, 카카오는 `is_email_verified` 인 이메일만 연결에 쓴다. `@social.expohub.local` 도메인은 일반 가입·주최자 생성이 함께 쓰는 등록 경로에서 막았다. 프론트는 카카오 `state` 를 추가·검증하고, `state` 를 `crypto.randomUUID()` 로 만든다.
- **검증**: `GoogleApiClientTest` 4종(우리 Client ID 토큰 통과, 다른 앱 토큰은 userinfo 호출 없이 거절, Client ID 미설정 시 거절, 4xx·5xx 구분), `GoogleLoginServiceTest`·`KakaoLoginServiceTest` 에 미검증 이메일·대체 이메일 선점 케이스 추가. 운영에는 서버 `.env` 에 `GOOGLE_CLIENT_ID` 를 먼저 넣은 뒤 배포했다. 값이 빠지면 구글 로그인만 실패하고 다른 로그인은 영향이 없다.
- **배운 점**: 외부 토큰은 "유효한가" 에 더해 "누구에게 발급됐나" 까지 확인한다. 이메일로 계정을 연결할 때는 검증된 이메일만 쓴다. 보안 설정이 빠지면 열리지 않고 닫히게 만든다.
- **근거**: PR #323 (`7dbb37a`), 선행 PR #318

### #9 주최자 예약 현황의 회차별 체크인 수가 항상 빈칸

- **증상**: 주최자 예약 현황의 체크인 수 칸이 항상 비어 있었다. 요구사항 시나리오 #8 을 충족하지 못했다.
- **원인**: ticket-service 에 회차별 체크인 집계 내부 API(`checkin-summary`)가 있었지만, expo-service 가 호출하지 않고 `checkedIn = null` 로 채웠다. 계약은 있었는데 호출하는 쪽이 없었다.
- **해결**: expo-service 가 호출해 회차별로 합친다(체크인이 없는 회차는 0). ticket-service 호출이 실패하면 **체크인 칸만 비우고 예약 현황은 그대로 보여준다.** 조회 화면에서 부가 정보 하나 때문에 전체가 실패하지 않게 하는 부분 실패 허용이다.
- **검증**: `ReservationSummaryApiTest` 2건 추가 — ticket 응답이 정상이면 회차별 합산(없는 회차 0), 실패하면 200 + `checkedIn: null`.
- **배운 점**: 서비스 간 계약은 제공하는 쪽과 호출하는 쪽을 함께 테스트한다. 조회의 실패 정책(fail-open·fail-closed)은 기능마다 명시한다.
- **근거**: PR #321 (`b24160f`)

### #3 Gemini 가 실패하면 "오후 3시 이후" 가 새벽 3시로 해석됨

- **증상**: 캘린더 AI 일정 추천에서 Gemini 호출이 실패하거나 한도를 넘기면 정규식 폴백을 쓰는데, "오후 3시 이후" 가 3시로, "오후 12시 이후" 가 0시로 해석돼 시간 조건이 사실상 무시됐다.
- **원인**: `RegexConstraintParser.toHour24()` 의 "오후" 분기가 비어 있었다. 평소에는 Gemini 가 해석해서 드러나지 않았고, 폴백 파서에는 테스트가 없었다.
- **해결**: 오후는 12를 더하고, 오후 12시는 정오(12시), 오전 12시는 0시로 둔다.

  | 입력 | 수정 전 | 수정 후 |
  | --- | --- | --- |
  | 오후 1~11시 | 1~11 | 13~23 |
  | 오후 12시 | 0 | 12 |
  | 오전 12시 | 0 | 0 |

- **검증**: `RegexConstraintParserTest` 신규(이 파서의 첫 테스트). 수정 전 코드로는 오후 케이스 5건이 실패하는 것을 먼저 확인했다.
- **배운 점**: 폴백은 평소에 실행되지 않아 결함이 숨는다. 폴백일수록 따로 테스트한다.
- **근거**: PR #340 (`2fc5daf`)

### #24 기능끼리 Gemini 무료 한도를 갉아먹고 429 가 남

- **증상**: AI 기능이 태깅·알림 문구·일정 추천·자연어 검색·소개글 초안·체크인 요약으로 늘면서 하루 무료 한도(1,500건)를 서로 갉아먹었고, 어느 기능이 한도를 쓰는지 알 수 없었다. 503 을 받고 바로 다시 보내면 429 가 났다.
- **원인**: ① 호출 상한·사용량 집계·캐시가 없었다. ② 처음 재시도 정책(#248)은 "4xx 는 즉시 중단" 이었는데, 429 는 4xx 이면서도 시간이 지나면 풀리는 일시적 오류라 재시도 대상이었다. ③ 503 직후 곧바로 재시도하면 같은 초에 두 번 호출해 429 를 우리가 만든다.
- **해결**: 공통 모듈 `common-ai` 에 하루 호출 상한과 기능별 사용량 로그, 같은 프롬프트 응답 캐시(LRU + TTL)를 넣었다(#248). 재시도는 5xx·타임아웃·**429 만** 하고, 재시도 전 대기를 시도마다 두 배로 늘린다(#294). 나머지 4xx 는 응답 본문(거부 사유)을 로그에 남기고 바로 멈춘다. 모든 AI 기능은 실패하면 `null` 을 돌려주는 fail-open 계약이라, AI 가 꺼져도 핵심 흐름은 동작한다. 운영에서 모델이 붐비면 `GEMINI_MODEL` 만 바꿔 컨테이너를 다시 올린다.
- **검증**: `common-ai` 첫 테스트 11건(MockRestServiceServer, 네트워크 없이 실행). 로컬에서 API 키를 뺀 상태로 AI 기능만 빠지고 서비스는 정상 동작하는 것을 확인했다.
- **배운 점**: 재시도는 오류 종류별로 정한다(영구적인 4xx 와 일시적인 429·5xx). 간격 없는 재시도는 그 자체로 부하가 된다.
- **근거**: PR #248 (`cb291c2`), PR #294 (`65c12ed`)

### #26 소셜 로그인 외부 호출이 DB 커넥션을 붙잡음

- **증상**: 코드 리뷰에서 발견했다. 소셜 제공자의 응답이 늦어지면 DB 커넥션 풀이 바닥나 일반 로그인까지 멈출 수 있는 구조였다.
- **원인**: `googleLogin`·`naverLogin`·`kakaoLogin` 이 `@Transactional` 안에서 **타임아웃 없이**(`RestClient.create()`) 제공자 API 를 호출했다. 트랜잭션이 시작되면 커넥션을 잡으므로, 외부 응답을 기다리는 동안 커넥션이 묶인다.
- **해결**: 세 메서드에서 `@Transactional` 을 빼고, 계정 연결·생성과 토큰 발급만 `TransactionTemplate` 으로 묶었다. `spring.http.client.connect-timeout: 2s`, `read-timeout: 3s` 를 설정하고(다른 서비스 내부 호출과 같은 값), 이 설정이 적용된 `RestClient.Builder` 를 주입받아 쓴다.
- **검증**: `KakaoLoginServiceTest` 2건 추가 — 카카오를 호출하는 동안 활성 트랜잭션이 없음, 요청 팩토리가 연결 2초·응답 3초. 수정 전 코드로는 둘 다 실패하는 것을 확인했다.
- **배운 점**: 트랜잭션 안에는 DB 작업만 둔다. 외부 호출에는 항상 타임아웃을 건다.
- **근거**: PR #330 (`b3ce2a9`)

## 5. JPA·마이그레이션

### #27 관심사를 같은 값으로 다시 저장하면 500

- **증상**: 마이페이지에서 이미 저장된 관심사를 유지한 채 다시 저장하면 "저장에 실패했습니다" 가 떴다. 운영 로그는 `Duplicate entry '21-KEYWORD-자동차' for key 'user_interests.uq_user_interest'` 였다.
- **원인**: 로직은 "기존 전부 삭제 → 새 목록 삽입" 이었다. 그런데 파생 삭제 메서드 `deleteAllByUserId` 는 삭제를 flush 때까지 미루고, IDENTITY 전략의 `save` 는 즉시 INSERT 한다. 옛 행이 남은 채 같은 값이 들어가 UNIQUE(`user_id`, `type`, `value`) 위반이 났다. 추천 점수 쪽 삭제도 같은 구조였다.
- **해결**: 두 삭제를 `@Modifying(flushAutomatically = true, clearAutomatically = true)` + `@Query` 벌크 삭제로 바꿔 즉시 실행되게 했다. 한 요청 안의 중복·공백 값도 걸러서 저장한다.
- **검증**: 기존 값을 유지한 재저장 성공, 요청 안의 중복·공백 제거 테스트 2건. 수정 전 코드로 운영 오류를 그대로 재현(실패)한 뒤 고쳤다.
- **배운 점**: JPA 의 실제 쓰기 순서는 코드 순서와 다르다(IDENTITY 저장은 즉시, 파생 삭제는 나중). 같은 키를 지우고 다시 넣는 로직은 벌크 연산으로 순서를 고정한다.
- **근거**: PR #334 (`14bc17b`)

### #23 공유 모듈의 마이그레이션 때문에 번호가 겹침

- **문제**: 예약 서비스에 `reservations` 테이블을 추가할 때(#75), 스키마의 다음 번호인 V2 로 만들면 Flyway 가 적용을 거절한다.

- **배운 점**: 여러 모듈이 한 스키마에 마이그레이션을 넣으면 번호 공간을 공유한다. 번호는 문서로 미리 정한다.

## 6. 배포·운영

### #7·#8 조회 이벤트·태그 조회가 운영에서만 404

- **증상**: 운영에서 박람회 조회 이벤트가 한 건도 기록되지 않았다(추천 점수 0.5점 누락). 조용한 호출이라 화면에는 아무 증상이 없었다. 박람회 상세의 태그 조회도 운영에서만 404 였다.
- **원인**: nginx 의 location 매칭 문제였다. `POST /api/v1/me/views/{id}` 는 더 넓은 `/api/v1/me/` 규칙에 걸려 identity-service 로 갔다. 태그 조회 `GET /api/v1/expos/{id}/tags` 규칙은 로컬 `nginx.conf` 에만 있고 운영 `nginx.prod.conf` 에는 없어서 expo-service 로 갔다. 로컬과 운영 설정 파일이 따로 관리되면서 어긋났다.
- **해결**: `nginx.prod.conf` 에 두 location 을 추가해 로컬 설정과 맞췄다. nginx 설정 변경은 web 컨테이너를 다시 만들어야 반영되므로 배포 확인 항목에 넣었다.
- **배운 점**: 조용한 호출의 실패는 아무도 모른다. 게이트웨이 라우팅은 운영 주소로 한 번씩 직접 확인한다. 비슷한 사례로 #22 의 후행 슬래시 문제가 있다.
- **근거**: PR #321 (`487a594`)

### #32 작은 인스턴스에서 서비스가 OOM 으로 기동 실패

- **증상**: 적은 메모리의 EC2 에서 서비스 4개와 MySQL 을 올리자 OOM 으로 기동에 실패했다(`ec2-setup.sh` 주석 기록).
- **원인**: 컨테이너 JVM 은 힙 상한을 따로 주지 않으면 크게 잡는다. 2GB 인스턴스 하나에 JVM 6개와 MySQL 을 올려야 했다.
- **해결**: 스왑 4GB 를 켜고(`vm.swappiness=10`), 서비스별 JVM 메모리를 명시했다. 기본 `-Xms64m -Xmx200m -XX:MaxMetaspaceSize=150m -Xss512k -XX:+UseSerialGC -XX:TieredStopAtLevel=1` 이고, 여섯 번째 JVM 인 recommendation-service 는 힙 160m 이다.
- **검증**: t3.small(2GB)에서 서비스 6개와 MySQL 을 운영 중이다. 2026-09-27 기준 메모리 사용 83%, 스왑 16% 다.
- **배운 점**: 컨테이너 JVM 은 힙·메타스페이스·스레드 스택을 명시한다. 여유가 적으니 서비스를 추가할 때 메모리 예산을 함께 정한다.
- **근거**: `infra/deploy/ec2-setup.sh`, `docker-compose.prod.yml` (`ec16fa5`, `9f84f76`)

### #33 인스턴스를 재시작하면 IP 가 바뀌어 접속·배포가 끊김

- **문제**: 비용 때문에 탄력적 IP 를 쓰지 않아, EC2 를 중지했다 시작하면 공인 IP 가 바뀐다. 도메인이나 CD(SSH 배포)가 옛 IP 를 가리키면 서비스와 배포가 함께 끊긴다.
- **해결**: 서버 cron 이 DuckDNS 를 갱신한다(`@reboot` 30초 뒤 1회 + 5분 주기, 토큰은 별도 파일). CD 의 `EC2_HOST` Secret 은 IP 가 아니라 도메인(`expohub.duckdns.org`)이다.
- **검증**: 2026-09-27 인스턴스를 중지·시작하는 시험을 했다. 공인 IP 가 바뀐 뒤 1~2분 안에 도메인이 새 IP 로 갱신됐고, 사이트가 정상 접속됐다. 이어서 실행한 CD 도 파일 복사·SSH 배포 단계까지 모두 성공해, `EC2_HOST` 가 도메인으로 설정돼 있음을 확인했다.
- **배운 점**: 고정 IP 가 없으면 사용자 접속과 배포 경로를 모두 이름(도메인)으로 통일하고, 재시작 시험으로 실제로 확인한다.
- **근거**: `docs/배포가이드.md` 2절

## 공통으로 얻은 규칙

1. **최종 방어선은 DB 다.** "검사 후 쓰기" 는 동시 요청에서 샌다. UNIQUE·조건부 UPDATE·행 잠금으로 막는다. (#4, #16, #29, #2)
2. **돈은 원장(PG)에 묻는다.** 로컬 상태나 클라이언트가 보낸 신호로 결제를 판단하지 않는다. (#5·#10, #21, #28)
3. **재시도할 실패는 예외가 아니라 기록으로 남긴다.** 롤백되면 재시도 장치가 실패를 모른다. (#11, #30)
4. **서비스 경계를 넘는 쓰기는 되돌릴 수 있는 쪽을 먼저 한다.** (#2)
5. **외부 호출은 트랜잭션 밖에서, 타임아웃과 오류별 재시도 정책을 갖고 한다.** (#24, #26)
6. **인가는 조회보다 먼저 하고, 응답 차이도 정보로 본다.** (#12, #25)
7. **평소에 안 도는 경로(모의 객체·폴백)는 따로 검증한다.** (#3, #21)
