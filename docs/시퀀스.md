## Story 1 — 회원가입·로그인

```mermaid
sequenceDiagram
    actor USER
    participant GW as Gateway
    participant ID as Identity-Service

    Note over USER,ID: 회원가입 (일반 USER)
    USER->>GW: POST /api/v1/auth/signup {email, password, name}
    GW->>ID: 회원가입 요청
    ID->>ID: 이메일 정규화(소문자·trim) + 비밀번호 정책 검증(8~64자, 영문+숫자)
    ID->>ID: 소셜 대체 이메일 도메인(@social.expohub.local)이면 400 거절
    alt 신규 이메일
        ID->>ID: 닉네임 생성 (실명 그대로, 이미 쓰이면 "실명#숫자")
        ID->>ID: users + user_roles(USER) 한 트랜잭션 저장
        ID-->>GW: 201 {userId, email, name, nickname, role: USER}
        GW-->>USER: 201
    else 이메일 중복
        ID-->>GW: 409 DUPLICATE_EMAIL (미생성)
        GW-->>USER: 409
    end

    Note over USER,ID: 로그인
    USER->>GW: POST /api/v1/auth/login {email, password}
    GW->>ID: 로그인 요청
    ID->>ID: 비밀번호 해시 대조 (미존재 이메일도 더미 해시와 비교해 응답 시간 동일)
    alt 인증 성공
        ID->>ID: Access Token 발급 (sub=userId, role=가장 높은 역할, exp=+1h)
        ID-->>GW: 200 {accessToken, tokenType: Bearer, expiresAt}
        GW-->>USER: 200
    else 이메일 미존재·비밀번호 불일치 (구분 불가)
        ID-->>GW: 401 INVALID_CREDENTIALS (WWW-Authenticate: Bearer)
        GW-->>USER: 401
    end

    Note over USER,ID: 이후 요청은 Authorization: Bearer {accessToken} 로 인증. Role은 JWT 클레임으로 전달돼 타 서비스가 조회 없이 참조.
```

> Refresh Token은 미구현이다. Access Token(1시간) 만료 시 재로그인한다. 실명(`name`)은 바꿀 수 없고 겹쳐도 되며, 화면에 보이는 닉네임(`nickname`)만 유일하다. 소셜 로그인(구글·카카오·네이버) 흐름은 아래 “소셜 로그인” 절 참조.

## Story 2 — 박람회 등록·회차 생성·공개

```mermaid
sequenceDiagram
    actor HOST
    participant GW as Gateway
    participant EX as expo-service
    participant RS as Reservation-Service
    participant AI as recommendation-service

    HOST->>GW: POST /api/v1/channels/{channelId}/expos
    GW->>EX: 박람회 생성 요청 (채널 소유자 확인)
    EX-->>GW: 201 {expoId, status: HIDDEN}
    GW-->>HOST: 201

    HOST->>GW: POST /api/v1/expos/{expoId}/rounds
    GW->>RS: 회차 생성 요청
    RS->>EX: GET /internal/v1/expos/{expoId} (소유권 확인, fail-closed)
    EX-->>RS: {channelOwnerId, status}
    RS-->>GW: 201 {roundId, sequence}
    GW-->>HOST: 201

    HOST->>GW: POST /api/v1/expos/{expoId}/publication
    GW->>EX: 공개 전환 요청
    EX->>RS: GET /internal/v1/rounds/exists?expoId={id} (회차 존재 확인, fail-closed)
    RS-->>EX: {exists: true}
    EX->>EX: 상태 HIDDEN → PUBLISHED
    EX-->>GW: 200 {status: PUBLISHED}
    GW-->>HOST: 200

    EX-)AI: POST /internal/v1/recommendations/expo-published {expoId, title, description, category} (커밋 후 비동기)
    Note over EX,AI: fail-open — AI 실패해도 공개 유지
    AI->>AI: LLM 태깅(최대 5개), 실패 시 분야별 기본 태그 (expo_tags 저장)
```

> 공개 중 제목·소개문을 수정하면 같은 방식으로 `POST /internal/v1/recommendations/expos/{expoId}/retag` 를 보내 태그를 다시 만든다.

## Story 2-b — 회차 수정·삭제

```mermaid
sequenceDiagram
    actor HOST
    participant GW as Gateway
    participant RS as Reservation-Service
    participant EX as expo-service

    HOST->>GW: PATCH /api/v1/expos/{expoId}/rounds/{roundId}
    GW->>RS: 회차 수정 요청
    RS->>EX: GET /internal/v1/expos/{expoId} (소유권 확인)
    EX-->>RS: {channelOwnerId, status}
    alt 삭제된 회차
        RS-->>GW: 404 NOT_FOUND (없는 회차로 취급)
    else 유효 예약 없고 시작 시각 미도래
        RS->>RS: 조건부 UPDATE (reserved_count = 0 일 때만)
        RS-->>GW: 200 {수정된 round}
    else 유효 예약 있음 또는 시작 시각 경과
        RS-->>GW: 409 ROUND_HAS_RESERVATIONS / ROUND_ALREADY_STARTED
    end
    GW-->>HOST: 응답 전달

    HOST->>GW: DELETE /api/v1/expos/{expoId}/rounds/{roundId}
    GW->>RS: 회차 삭제 요청
    RS->>EX: GET /internal/v1/expos/{expoId} (소유권·공개 상태 확인)
    EX-->>RS: {channelOwnerId, status}
    alt 시작 시각 미도래
        RS->>RS: ① 소프트 삭제 먼저 (조건부 UPDATE: 유효 예약 0건일 때만 deleted_at 기록, 행 잠금)
        alt 유효 예약 있어 0행
            RS-->>GW: 409 ROUND_HAS_RESERVATIONS (박람회 상태 불변)
        else 삭제 성공, 공개 박람회의 마지막 회차
            RS->>EX: ② PATCH /internal/v1/expos/{expoId}/unpublish (비공개 전환은 나중에)
            EX-->>RS: 200 {expoId, status: HIDDEN}
            Note over RS,EX: 비공개 전환 실패 시 예외 → ① 소프트 삭제까지 함께 롤백
            RS-->>GW: 204
        else 삭제 성공, 다른 회차 남음
            RS-->>GW: 204
        end
    else 시작 시각 경과
        RS-->>GW: 409 ROUND_ALREADY_STARTED
    end
    GW-->>HOST: 응답 전달
```

> 되돌릴 수 있는 로컬 삭제를 먼저, 되돌릴 수 없는 원격 비공개를 나중에 한다. 순서가 반대면 예약이 있어 삭제가 거절될 때마다 박람회만 숨겨진 채 남는다.

## Story 5 — 예약·결제·QR 발급

```mermaid
sequenceDiagram
    actor MEMBER
    participant GW as Gateway
    participant RS as Reservation-Service
    participant EX as expo-service
    participant PG as PortOne (테스트 채널, 실제 API)
    participant TK as Ticket-Service
    participant AI as recommendation-service

    MEMBER->>GW: POST /api/v1/rounds/{roundId}/reservations {headcount 1~7, contactName, contactPhone}
    GW->>RS: 예약 생성 요청 (USER 만)

    RS->>EX: GET /internal/v1/expos/{expoId} (공개 여부 확인, fail-closed)
    EX-->>RS: {status: PUBLISHED}

    RS->>RS: 정원 차감 (조건부 UPDATE, 부족하면 409 CAPACITY_EXCEEDED)
    RS->>RS: 예약 저장 (active_holder UNIQUE — 같은 회원 동시 요청은 409 DUPLICATE_RESERVATION, 정원 롤백)
    alt 참가비 0원
        RS->>RS: 즉시 CONFIRMED (결제 단계 생략)
    else 유료
        RS->>PG: 결제 사전 등록 (금액 고정)
        PG-->>RS: 등록 완료
        RS-->>GW: 201 {reservationId, reservationNo, status: PENDING, expiresAt(+10분), paymentId}
    end
    GW-->>MEMBER: 201

    MEMBER->>PG: 결제창에서 결제 (브라우저 SDK)
    MEMBER->>GW: POST /api/v1/reservations/{reservationId}/payment (결제창 닫힌 뒤)
    GW->>RS: 결제 확정 요청
    RS->>PG: 결제 단건 조회 (금액·상점·채널 검증)
    alt PAID
        PG-->>RS: 결제 완료
        RS->>RS: PENDING → CONFIRMED (멱등 함수 — 웹훅·만료 배치도 같은 함수)
        RS-->>GW: 200 {status: CONFIRMED}
    else FAILED/CANCELLED
        RS->>RS: PENDING → CANCELLED, 정원 반환
        RS-->>GW: 200 {status: CANCELLED}
    else 모름(무응답)
        RS-->>GW: 503 DEPENDENCY_UNAVAILABLE (상태 불변)
    end
    GW-->>MEMBER: 응답 전달

    Note over RS,TK: 커밋 후 티켓 통지 큐가 발송
    RS->>RS: 예약 행 잠금 → 아직 CONFIRMED 인지 확인 (취소됐으면 발급 포기)
    RS-)TK: POST /internal/v1/tickets {reservationId, reservationNo, expoId, roundId, userId, headcount}
    TK-->>RS: 201 {ticketId, checkinToken, status: ISSUED} (reservationId UNIQUE 로 멱등)
    Note over RS,TK: fail-open — 실패 시 1분→16분 지수 백오프로 최대 6회 재시도, 예약은 CONFIRMED 유지

    RS-)AI: POST /internal/v1/recommendations/events {eventType: RESERVATION_CONFIRMED, reservationId, reservationNo} (커밋 후 비동기)
    Note over RS,AI: fail-open — 취향 점수 반영 + 예약 확정 알림 생성
```

> PortOne 웹훅(`POST /api/v1/reservations/webhooks/portone`)도 같은 확정 함수를 탄다. 서명을 검증하고, 결제 결과를 알 수 없으면 503 을 주되 웹훅을 처리 완료로 적지 않아 재전송이 다시 처리된다. 결제대기 예약은 2분 주기 배치가 만료 시각(+10분)이 지난 건을 PG에 다시 조회해, 결제됐으면 확정하고 아니면 EXPIRED 로 정리한다.

## Story 7 — 현장 체크인

```mermaid
sequenceDiagram

    Note over TK,AI: fail-open — AI 실패해도 체크인 유지

    Note over HOST,TK: 잘못 처리 시: POST /api/v1/tickets/{ticketId}/checkin/cancellation (USED → ISSUED, 시간창 무관, 같은 잠금)
```

## Story 8 — 예약 취소·환불

```mermaid
sequenceDiagram
    actor MEMBER
    participant GW as Gateway
    participant RS as Reservation-Service
    participant PG as PortOne
    participant TK as Ticket-Service

    MEMBER->>GW: PATCH /api/v1/reservations/{reservationId}/cancellation

    RS->>RS: 회차 시작 전인지 확인 (지났으면 400 CANCELLATION_DEADLINE_PASSED)
    alt 결제대기(PENDING) 예약
        RS->>PG: 결제 단건 조회 (결제창은 닫혔는데 확정 전일 수 있다)
        PG-->>RS: PAID / 미결제

        RS->>TK: GET /internal/v1/tickets/reservation/{reservationId} (입장 여부 확인, fail-closed)
        TK-->>RS: {status: ISSUED}
        Note over RS,TK: USED 면 409 ALREADY_CHECKED_IN, 조회 실패면 503
    end

    RS->>RS: 예약 상태 → CANCELLED, 정원 반환 (1회)

        alt 환불 성공
            PG-->>RS: 환불 완료
            RS-->>GW: 200 {status: CANCELLED, refundState: REFUNDED}

            RS->>RS: REFUND_FAILED 기록 (취소는 유지)
            RS-->>GW: 200 {status: CANCELLED, refundState: REFUND_PENDING}

        end
    else 환불 기한 초과
        RS-->>GW: 200 {status: CANCELLED, refundState: NOT_REFUNDABLE}
    end
    GW-->>MEMBER: 200

    Note over RS,TK: 커밋 후
    RS-)TK: PATCH /internal/v1/tickets/reservation/{reservationId}/revoke (QR 무효화, fail-open, 최대 12회 재시도)
```

## Story 10 — VIP 배너 신청·결제

```mermaid
sequenceDiagram
    actor HOST
    participant GW as Gateway
    participant EX as expo-service
    participant PG as PortOne

    HOST->>GW: POST /api/v1/expo-promotions {expoId}
    GW->>EX: 배너 신청 (ORGANIZER, 채널 소유자)
    EX->>EX: 박람회가 PUBLISHED 인지 (아니면 409 PROMOTION_EXPO_NOT_PUBLISHED)
    EX->>EX: ACTIVE 수 < 10 (아니면 409 PROMOTION_SLOT_FULL), 같은 박람회 ACTIVE 없음
    opt 이전 PENDING 신청이 남아 있음
        EX->>PG: 이전 결제 단건 조회
        Note over EX,PG: 결제됐으면 환불 후 취소, 아니면 취소만
    end
    EX->>EX: ExpoPromotion PENDING 생성
    EX->>PG: 결제 사전 등록 (9,900원)
    EX-->>GW: 201 {promotionId, paymentId, amount: 9900, status: PENDING}
    GW-->>HOST: 201

    HOST->>PG: 결제창에서 결제 (브라우저 SDK)
    HOST->>GW: POST /api/v1/expo-promotions/{promotionId}/payment (결제창 닫힌 뒤)
    GW->>EX: 결제 확인 요청
    EX->>PG: 결제 단건 조회 (금액 검증)
    alt PAID
        EX->>EX: ACTIVE 수 다시 확인
        alt 슬롯 남음
            EX->>EX: PENDING → ACTIVE
            EX-->>GW: 200 {status: ACTIVE}
        else 그사이 가득 참
            EX->>PG: 방금 결제 환불
            EX->>EX: PENDING → CANCELLED
            EX-->>GW: 200 {status: CANCELLED}
        end
    else FAILED
        EX->>EX: PENDING → CANCELLED
        EX-->>GW: 200 {status: CANCELLED}
    else 모름
        EX-->>GW: 503 (상태 불변)
    end
    GW-->>HOST: 응답 전달

    Note over HOST,EX: 환불: POST /api/v1/expo-promotions/{promotionId}/refund — 배너를 먼저 CANCELLED 로 내리고 PG 환불, 실패는 재시도 큐
```

> PortOne 웹훅(`POST /api/v1/expo-promotions/webhooks/portone`)도 서명 검증 후 같은 확인 함수를 탄다. 활성 배너 조회(`GET /api/v1/expo-promotions/active`)는 ACTIVE 이면서 박람회가 PUBLISHED 인 것만 30초 단위로 순환해 돌려주고, 결제 후 30일 또는 박람회 마감은 매일 자정 배치가 EXPIRED 로 정리한다.

## Story AI — 맞춤 추천 조회 (Sprint 3~4 신규)

## 소셜 로그인 (Sprint 4 신규)

```mermaid
sequenceDiagram
    actor USER
    participant FE as 프론트엔드
    participant GW as Gateway
    participant ID as Identity-Service
    participant OP as 소셜 제공자<br/>(구글·카카오·네이버)

    Note over USER,OP: 구글 = 액세스 토큰 방식 / 카카오·네이버 = 인가 코드 방식

    USER->>FE: 소셜 로그인 버튼 클릭
    alt 구글 (토큰 방식)
        FE->>OP: 팝업 로그인 → 액세스 토큰 수신
        FE->>GW: POST /api/v1/auth/google {googleAccessToken}
    else 카카오·네이버 (코드 방식)
        FE->>OP: 팝업 인가 (state 포함) → 콜백에서 code 수신 (postMessage)
        Note over FE: 팝업을 닫으면 0.5초 안에 로그인 대기 취소
        FE->>GW: POST /api/v1/auth/kakao {code, redirectUri, state}<br/>또는 /naver {code, state}
    end

    GW->>ID: 소셜 로그인 요청
    Note over ID,OP: 제공자 호출은 DB 트랜잭션 밖, 연결 2s·응답 3s
    opt 구글
        ID->>OP: tokeninfo 로 토큰 aud = 우리 GOOGLE_CLIENT_ID 검증
        Note over ID,OP: aud 불일치 or GOOGLE_CLIENT_ID 미설정 → 401 거절(fail-closed)
    end
    ID->>OP: 토큰 교환(코드 방식) + 사용자 정보(userinfo) 조회
    alt 조회 성공
        OP-->>ID: {provider_id, email, verified 여부, name}
        ID->>ID: 이메일 검증 확인 (구글 verified_email / 카카오 is_email_verified)
        Note over ID: 미검증 이메일은 기존 회원 연결 금지 → placeholder(kakao_{id}@social.expohub.local)
        ID->>ID: 트랜잭션 시작 — oauth_accounts에서 (provider, provider_id) 조회
        alt 기존 연결 있음
            ID->>ID: 연결된 회원으로 로그인
        else 신규
            ID->>ID: 검증된 email 이 같은 회원이면 연결, 아니면 새 회원(USER, password_hash = NULL, 닉네임 자동 생성) + oauth_accounts INSERT
        end
        ID-->>GW: 200 {accessToken, tokenType, expiresAt}
        GW-->>USER: 200 (일반 로그인과 동일 토큰)
    else 조회 실패·검증 실패
        OP-->>ID: 오류/무응답
        ID-->>GW: 401 SOCIAL_LOGIN_FAILED 또는 503 DEPENDENCY_UNAVAILABLE
        GW-->>USER: 401/503
    end
```

> 검증된 이메일만 기존 회원과 연결한다(#323). 미검증·무이메일은 placeholder(`@social.expohub.local`)로 처리하고, 이 도메인으로는 일반 가입도 막아 계정 연결 선점을 차단한다. 세 provider 모두 `(provider, provider_id)`가 oauth_accounts에 유일하게 저장되어 같은 소셜 계정이 두 회원에 붙지 않는다. 프론트는 카카오·네이버 인가 요청에 `state`(`crypto.randomUUID`)를 붙여 CSRF를 방지한다. 소셜 가입 회원은 `GET /users/me` 의 `hasPassword=false` 로 비밀번호 변경 화면이 숨겨진다.

## 실패·복구 흐름

| 시나리오 | 실패 지점 | 처리 방식 |
| --- | --- | --- |
| 결제 요청 후 PG 응답 없음 | RS ↔︎ PG | 결제 확정 요청은 503(상태 불변). 2분 주기 배치가 만료 시각(+10분)이 지난 PENDING 을 PG에 다시 조회해 결제됐으면 확정, 아니면 EXPIRED 처리·정원 반환. PG 응답을 모르면 10분 유예 뒤 재시도 |
| 웹훅 수신 중 PG 조회 실패 | PG → RS/EX | 503 으로 재전송 요청. 웹훅 기록을 RECEIVED 로 남겨 재전송이 중복으로 걸러지지 않고 다시 처리된다 |
| QR 발급 실패 (Ticket-Service 불응답) | RS → TK | 커밋 후 큐에서 1·2·4·8·16분 백오프로 최대 6회 재시도 → 실패 시 예약 CONFIRMED 유지, QR 없음 표시. 재시도 전 예약이 취소됐으면 발급 포기 |
| QR 무효화 실패 | RS → TK | 취소는 완료, 무효화만 최대 12회(최대 1시간 간격) 재시도 — “취소된 예약으로 입장”이 발급 실패보다 나쁘므로 더 길게 |
| 환불 실패 | RS/EX → PG | 취소(배너는 내림)는 완료 처리, 환불만 1분 주기·최대 6회 배치 재시도. 전부 실패 시 REFUND_UNRESOLVED 로 남겨 운영자 수동 처리 |
| 결제대기 예약 취소 시 결제 여부 불명 | RS → PG | PG 단건 조회 결과가 “모름”이면 환불 없이 취소만 한다 (만료 배치가 뒤에 다시 확인) |
| 배너 켜는 순간 슬롯 초과 | EX | 방금 받은 결제를 환불하고 배너를 CANCELLED 로 둔다 |
| 체크인 중 Reservation-Service 불응답 (시간창 조회) | TK → RS | fail-open — 시간창 검증만 생략하고 체크인 허용, WARN 로그 기록 |
| 체크인 중 expo-service 불응답 (소유권 조회) | TK → EX | fail-closed — 503 반환, 체크인 거절 |
| 체크인 이력 기록 실패 | TK | 체크인은 유지(커밋 후 별도 트랜잭션), WARN 로그 |
| Settlement-Service에서 Reservation-Service·expo-service 불응답 | ST → RS/EX | fail-closed — 정산 조회 실패 응답 반환. 부분 합산 없음 |
| 자동 마감 스케줄러 중 Reservation-Service 불응답 | EX → RS | 이번 주기 건너뛰고 10분 뒤 재시도. 옛 버전과 섞여 커서가 전진하지 않으면 루프 중단 |
| recommendation-service 불응답 (박람회 태깅·재태깅) | EX → AI | fail-open — 무시, 태그 없는 상태로 공개 유지 (추천 매칭에서 해당 박람회 제외될 수 있음) |
| recommendation-service 불응답 (행동 이벤트) | RS/TK → AI | fail-open — 무시, 예약·체크인 정상 완료 (재시도 없음) |
| expo-service 불응답 (추천 목록·알림 배치) | AI → EX | 200 + `items: []` 반환 / 그날 추천 알림 건너뜀 |
| Gemini 실패 (자연어 검색) | EX → GeminiClient | fail-open — 문장 전체를 키워드로 검색 |
| Gemini 실패 (소개글 초안) | EX → GeminiClient | fail-open — 200 `{description: null, applied: false}` 반환 |
| Gemini 실패 (캘린더 제약 해석) | RS → GeminiClient | fail-open — 규칙 해석 → 조건 없이 그리디 실행 |
| Gemini 실패 (체크인 결과 요약·정산 요약) | TK/ST → GeminiClient | fail-open — 수치는 표시하고 요약만 null |
| 소셜 제공자 불응답 | ID → OP | 503 — 해당 제공자 로그인만 실패, 이메일 로그인 무영향. DB 커넥션을 잡지 않아 다른 요청에 영향 없음 |
