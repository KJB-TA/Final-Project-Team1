# 권한 Matrix — 박람회 예약 관리 플랫폼

## Role 정의 — Sprint 1

| Role | 주체 | Sprint 1에서의 획득 경로 |
| --- | --- | --- |
| (없음) | 비인증 방문자 | 로그인하지 않은 상태. 만료·위조된 Token 도 비인증과 같게 취급한다 |
| `USER` | 회원 | `signUp`으로 가입 시 자동 부여 (Sprint 4부터 소셜 계정 첫 로그인 시에도 자동 부여) |
| `ORGANIZER` | 주최자 | `createOrganizer`로 전체관리자가 발급 시 부여 (Sprint 3부터 주최자 신청 승인으로도 부여) |
| `SUPER_ADMIN` | 전체관리자 | Identity-Service V2 Migration seed로 초기 1건 생성. 비밀번호 Hash는 환경 변수로 주입하며 Repository에 남기지 않는다 |
| 내부 Service | Nginx를 거치지 않는 Service 간 직접 호출 | 모든 Service가 공유하는 환경 변수 `INTERNAL_TOKEN` 하나를 Bearer Token으로 부착 |

> JWT 의 `role` 클레임에는 사용자가 가진 역할 중 가장 높은 것 하나만 실린다. 모든 역할 검사는 정확히 일치해야 통과하며, 상위 역할이 하위 역할의 권한을 물려받지 않는다 — 전체관리자도 예약·채널 기능은 403 이다.

## 판정 순서

1. **인증 유효성** — 각 Service가 common-security의 JwtAuthenticationFilter로 JWT의 서명·만료를 검증한다. 필터는 요청을 거절하지 않고, 누락·만료·서명 오류 Token 은 모두 비인증으로 취급한다. 보호 기능은 각 Service 가 인증 주체가 없으면 `WWW-Authenticate: Bearer` Header가 있는 401로 거절한다.
2. **Role** — 데이터를 소유한 Service가 JWT 클레임의 `role`로 판단한다. 정확히 일치해야 하며 상위 역할 상속은 없다. 부족하면 403. Resource 조회보다 먼저 판정해, 역할이 없는 주체가 404/403 차이로 Resource 존재 여부를 알아내지 못하게 한다.
3. **Resource 존재와 소유 관계** — 소유권은 데이터를 소유한 Service가 최종 판단한다.
4. **업무 상태** — 박람회 상태, 회차 존재 여부, 정원·시각 유효성을 확인한다. 요청 형식 검증(400)은 Controller 단계에서 가장 먼저 일어날 수 있다.
5. **Dependency 결과** — 내부 호출과 소셜 제공자 호출은 연결 2s · 응답 3s Timeout(recommendation-service → expo-service 는 응답 5s). 결과를 확인할 수 없으면 닫는 쪽으로 실패한다(recommendation-service 연동과 표시용 조회 제외 — fail-open).
6. **허용 또는 안전한 실패**

## 실패 정책의 근거

**403과 404를 나누는 기준.** 비인증 방문자가 `HIDDEN`·`CLOSED` 박람회를 직접 조회하거나, 회원이 타인의 예약을 조회·취소하면 **404** — 존재 자체를 노출하지 않기 위함. 주최자가 다른 주최자의 채널·박람회에 쓰기·관리 동작을 하면 **403**. 단 주최자 박람회 목록·단건·수정과 소개글 초안은 다른 주최자의 채널을 **404** 로 숨긴다.

**Dependency 장애를 권한 없음으로 오인시키지 않습니다.** 내부 호출이 Timeout·실패하면 403이 아니라 **503**을 반환하고 Trace ID를 함께 줍니다.

**recommendation-service 연동은 모두 fail-open.** 추천·태깅·이벤트 수집 실패가 예약·체크인 등 핵심 기능에 영향을 줘서는 안 됩니다.

**이중결제 방지 — “실패확정”과 “모름”을 구분합니다.** PG가 명시적으로 결제 거절하면 `CANCELLED`, PG가 무응답이면 상태를 그대로 유지합니다. “모름”으로 끝난 웹훅은 처리 완료로 기록하지 않아, PG 의 재전송이 실제로 다시 처리됩니다.

**화면이 알려온 결제는 믿지 않습니다.** 예약이든 배너든 화면은 “결제창이 닫혔다”만 알리고, 결제 사실과 금액은 서버가 PG 에 직접 확인한 뒤에만 상태를 바꿉니다.

**동시 요청은 DB 가 막습니다.** 정원 초과와 회원당 중복 예약은 서비스 검사에 더해 조건부 UPDATE·UNIQUE 제약이 최종 방어선이며, 위반은 같은 409 로 응답합니다.

**부수 효과는 커밋 뒤에만 남깁니다.** 체크인 이력·추천 이벤트·티켓 발급 통지는 주 트랜잭션이 확정된 뒤 보내므로, 요청이 실패(롤백)했는데 흔적만 남는 일이 없습니다.

**AI 호출 실패는 권한·업무 실패가 아닙니다.** LLM 이 실패해도 요청은 200 으로 성립하고, AI 가 만든 부분만 비거나 규칙 기반 결과로 대체됩니다.
